# ADR-002：LLM 不得直接批准或执行采购

- 状态：Accepted
- 日期：2026-09-21
- 决策范围：采购审批、关键业务写操作、Agent Tool 边界

## 1. 背景

据衡需要使用 LLM 从报价单、采购制度、供应商档案、历史价格和合同中提取信息、解释风险并生成审批建议。LLM 能处理非结构化文本，但它的输出具有概率性，也可能受到以下问题影响：

- 幻觉、遗漏或对金额和条款的错误理解。
- Prompt Injection 或恶意材料中的指令。
- 无法可靠判断当前用户、组织和审批权限。
- 模型升级、Prompt 修改和采样造成结果波动。
- 外部服务超时、截断、格式变化或降级。
- 无法仅凭自然语言输出证明某次授权由谁作出。

采购批准、驳回、预算占用、订单创建和付款属于重要业务状态变化。若模型可以直接执行这些操作，系统将无法提供稳定权限边界、幂等行为、责任归属和审计证据。

## 2. 决策

LLM 和 Agent 不拥有最终审批权，也不得直接执行重要采购业务操作。

模型输出一律视为**不可信的候选信息或建议草稿**。任何重要状态变化必须由有权限的人员明确发起，并由确定性服务端代码完成认证、授权、输入、业务状态、并发和幂等校验后执行。

该限制必须在服务端和 Tool 注册边界强制执行，不能只依赖 Prompt、前端确认框或团队约定。

## 3. 允许的 LLM 行为

在满足数据范围和校验要求的前提下，LLM 可以：

- 从受支持材料中提取候选字段。
- 对采购申请和材料进行摘要。
- 解释已经由确定性规则识别的风险。
- 提出可能的风险或材料缺口，供规则或人工复核。
- 使用只读 Tool 检索采购制度、供应商档案、预算、历史采购和合同证据。
- 生成带引用的审批建议草稿。
- 生成待补充材料清单或人工复核问题。

允许生成“建议批准”“建议驳回”等文字，但这些内容只能保存在明确标记为建议/草稿的结构中，不能被解释为审批结果。

## 4. 禁止的 LLM 行为

LLM 或 Agent 不得：

- 将采购申请状态改为已批准或已驳回。
- 代表用户确认审批、签署合同或接受条款。
- 扣减、冻结或重新分配预算。
- 创建或发送正式采购订单。
- 发起付款、退款或修改收款账户。
- 创建自己的权限、提升角色或扩大数据访问范围。
- 把聊天记录、Prompt 或 Agent Memory 写成正式业务事实。
- 绕过必填校验、金额阈值、审批层级、幂等或并发控制。
- 修改或删除审计记录以掩盖已发生操作。

若未来出现新的关键写操作，默认归入禁止范围，直到新的 User Story 和 ADR 明确允许其最小边界。

## 5. 强制执行方式

### 5.1 能力隔离

- Agent 初期只注册只读 Tool。
- 批准、驳回、预算、订单和付款能力不实现为模型可调用 Tool。
- 第一个可考虑的写 Tool 只能是 `createPurchaseApprovalDraft`，且它创建的是草稿，不是决定。
- Tool 不能接受由模型自由指定的当前用户、角色或组织范围。

### 5.2 可信运行时上下文

服务端从认证上下文和当前业务流程注入：

- 当前用户 ID。
- 当前角色及授权范围。
- 当前组织/部门 ID（若该 Story 已引入）。
- 当前采购申请 ID。
- 当前 Agent Run ID。

模型参数与上述上下文冲突时，服务端必须拒绝请求或使用可信上下文，不能接受模型覆盖。

### 5.3 结构化校验

模型输出进入业务应用前必须经过：

1. JSON/Schema 和必填字段校验。
2. 类型、枚举白名单和长度校验。
3. 金额、比例、日期及数值范围校验。
4. 业务对象存在性和数据范围校验。
5. 引用存在性及引用是否支持结论的校验。
6. 与当前业务状态和确定性规则的一致性检查。

校验失败的业务型结果进入失败、待补充或人工复核状态，不得把原始自然语言直接写入领域表作为事实。

### 5.4 人工命令路径

批准或驳回必须遵循以下流程：

```text
审批人查看申请、证据、风险和建议
  -> 审批人明确提交批准/驳回命令
  -> 服务端从认证上下文取得操作者
  -> 校验任务归属、角色和数据范围
  -> 校验申请状态、版本、输入和幂等键
  -> 在事务中执行领域状态转换
  -> 同一事务写入审批结果和审计记录
  -> 返回最终业务结果
```

模型建议、模型 Tool 调用、自然语言中的“我确认”或由模型生成的 token 均不能替代审批人的明确命令。

### 5.5 幂等、并发和审计

- 关键命令携带服务端可验证的幂等标识。
- 幂等记录绑定调用者、操作类型和目标对象；不同载荷复用同一标识应报冲突。
- 版本/条件更新确保两个并发审批最多一个成功。
- 审批结果与审计记录在同一数据库事务中保存。
- 审计至少记录操作者、动作、目标、时间、结果、请求标识和必要证据引用。

## 6. 信任边界示意

```text
材料 / 用户问题
      |
      v
只读检索与受限上下文
      |
      v
LLM / Agent（不可信计算）
      |
      v
结构化候选结果
      |
      v
Schema + 业务 + 引用校验
      |
      v
审批建议草稿 --------> 审批人查看并明确决定
                              |
                              v
                    确定性服务端命令
                    权限 + 状态 + 幂等 + 并发
                              |
                              v
                       状态与审计记录
```

图中的 LLM 路径无法直接到达最终状态写入。

## 7. 失败与降级规则

- 模型不可用：核心采购申请和人工审批能力仍可运行；AI 分析显示不可用或待处理。
- 输出格式错误：拒绝接纳并按策略重试或转人工复核。
- 证据不足：列出缺失项，不生成确定的批准结论。
- 引用无效：对应风险解释或建议不能进入可供审批依赖的已验证状态。
- Tool 越权：立即拒绝，记录安全事件所需的最小信息，不执行部分写操作。
- 达到 Agent 步数、调用次数或时间预算：以明确终止状态结束，不自动放行。

## 8. 后果

### 8.1 正面影响

- 审批责任归属于明确的人和服务端命令。
- 模型波动或 Prompt Injection 无法直接改变关键业务状态。
- 权限、幂等、并发和审计可以通过确定性测试证明。
- 可以独立替换模型，而不改变审批状态机。
- AI 不可用时仍保留基础业务闭环。

### 8.2 成本与限制

- 用户必须执行一次明确的人工确认，无法实现全自动采购批准。
- 需要维护建议/草稿与正式决定的独立数据结构和状态。
- Application Service 需要额外的权限、幂等、并发和审计逻辑。
- AI 提取结果需要校验与复核，增加了实现和测试成本。

这些成本是企业采购授权可解释、可追责所必需的。

## 9. 被拒绝的方案

### 9.1 允许 Agent 在置信度高时自动审批

拒绝原因：模型置信度不是权限证明，也不能保证事实正确、规则完整或请求未被注入攻击。

### 9.2 用 Prompt 声明“不要越权”作为唯一保护

拒绝原因：Prompt 不是强制安全边界，可能被材料内容、用户输入或模型行为绕过。

### 9.3 前端弹窗确认后直接执行模型 Tool

拒绝原因：前端可被绕过，也不能替代服务端对操作者、状态、幂等和并发的重新校验。

### 9.4 模型返回 `APPROVED` 后由服务端自动映射状态

拒绝原因：这只是把直接审批藏在映射代码中，仍然由概率性输出决定关键业务状态。

## 10. 验证要求

实现相关 Story 时至少验证：

- Agent 的可用 Tool 列表中不存在批准、驳回、预算、订单或付款操作。
- 模型输出 `APPROVED`、伪造审批人或注入调用指令时不会改变采购状态。
- 创建审批草稿和执行审批是两条不同的服务端用例。
- 未认证、错误角色、错误任务范围和申请人自审均被拒绝。
- 重复请求和并发审批最多产生一个有效决定。
- 决定和审计记录同时提交或同时回滚。
- 模型超时、格式错误、无引用和证据不足均进入明确的非批准状态。

详细测试方法见 `docs/TEST_STRATEGY.md`。
