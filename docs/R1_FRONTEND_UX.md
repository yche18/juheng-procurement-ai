# 据衡 R1 前端 UX 基线

- 文档状态：Baselined
- 版本：1.0
- 日期：2026-09-23
- 适用范围：`FE-000`、`FE-010`～`FE-017`

## 1. 目的与边界

本文定义 R1 React 演示客户端的页面、导航、角色入口和用户可见状态。业务权限、状态机、金额、版本、幂等和最终决定仍由服务端控制；本文引用现有 User Story，不重新定义采购业务规则。

R1 前端目标是让已经完成的后端能力形成可完整演示的业务应用，不建设完整企业管理后台、生产认证平台、移动端、国际化、材料、分析、RAG 或 Agent 页面。

## 2. 用户与会话

### 2.1 演示认证

- 用户在 `/login` 输入用户名和密码。
- 客户端只在运行时内存中保留 Basic Auth 凭据，并调用 `GET /api/current-user` 验证身份和取得完整角色集合。
- 凭据不进入 Redux State、Redux DevTools、URL、日志、`localStorage` 或 `sessionStorage`。
- 页面刷新会清空凭据并返回登录页，这是 R1 本地演示认证的已知限制，不伪装成生产登录体验。
- `AUTHENTICATION_REQUIRED` 清理当前内存凭据和会话；`ACCESS_DENIED` 只显示无权状态，不自动退出。

### 2.2 多角色用户

同一用户可以同时拥有 `REQUESTER` 和 `APPROVER`。登录后导航展示其全部可用业务入口，不把用户压缩成单一“当前角色”。`ADMIN` 在 R1 没有业务页面；只有 `ADMIN` 的用户看到明确的“当前版本无管理功能”状态，而不是进入申请或审批页面。

## 3. 应用外壳与导航

```text
App Shell
├─ Header
│  ├─ 产品名称
│  ├─ 当前用户
│  ├─ 角色标签
│  └─ 退出
├─ Role-aware Navigation
│  ├─ 我的申请（REQUESTER）
│  └─ 审批任务（APPROVER）
└─ Main Content
```

退出只清理浏览器内存中的凭据、Session State 和 RTK Query Cache，不改变任何服务端业务数据。

## 4. 路由

| 路由 | 主要角色 | 页面 |
| --- | --- | --- |
| `/login` | 未认证用户 | 演示登录 |
| `/requester/requests` | `REQUESTER` | 我的采购申请列表 |
| `/requester/requests/new` | `REQUESTER` | 创建采购申请 |
| `/requester/requests/:requestId` | 创建者 | 采购申请详情与审计时间线 |
| `/requester/requests/:requestId/edit` | 创建者且状态为 `DRAFT` | 编辑采购草稿 |
| `/approver/tasks` | `APPROVER` | 分配给我的审批任务 |
| `/approver/tasks/:taskId` | 任务受理人 | 审批任务详情、决定操作与审计时间线 |
| `/403` | 已认证用户 | 当前入口无权访问 |
| `*` | 任意 | 页面不存在 |

路由限制只改善体验。直接输入 URL 时仍调用服务端 API，由服务端决定是否拥有数据范围；前端不能依据路径参数自行认定所有权或任务归属。

## 5. 申请人页面

### 5.1 我的申请列表

对应 `US-011`、`FE-011`。

页面内容：

- 状态筛选：全部、`DRAFT`、`SUBMITTED`、`APPROVED`、`REJECTED`。
- 从零开始的服务端分页；URL 保存 `page`、`size` 和可选 `status`。
- 列表展示业务编号、标题、部门、期望交付日期、预计总额、状态和更新时间。
- 默认排序完全采用服务端结果，前端不再次重排。
- 空结果区分“当前没有申请”和“当前筛选无结果”。
- 创建按钮进入 `/requester/requests/new`。

### 5.2 创建采购申请

对应 `US-010`、`FE-010`。

表单字段：

- 标题、采购目的、申请部门、期望交付日期。
- 至少一个采购项；每项包含名称、受控品类、规格、数量、计量单位和预计单价。
- R1 受控品类为 `LAPTOP`、`MONITOR`、`OFFICE_CHAIR`、`SOFTWARE_LICENSE`。
- 允许增加和删除采购项，但不能删除到零项。
- 客户端校验与 API Contract 对齐，只用于即时反馈；服务端 `VALIDATION_FAILED` 仍是最终结果。
- 前端不计算权威行金额或预计总额；创建成功后展示服务端计算结果并进入详情页。

创建请求进行中时禁用重复提交。网络结果不确定时不自动再次创建草稿，由用户明确重试；创建用例当前没有幂等键，页面必须说明重复点击风险由进行中禁用控制，而不是宣称具备服务端幂等。

### 5.3 申请详情

对应 `US-011`、`US-013`、`US-016`、`US-017`。

公共内容：业务编号、标题、目的、部门、交付日期、币种、服务端预计总额、版本、创建/更新时间和采购项。

| 申请状态 | 页面行为 |
| --- | --- |
| `DRAFT` | 显示编辑和提交入口；数据仍以详情响应为准 |
| `SUBMITTED` | 核心字段只读，显示等待人工审批 |
| `APPROVED` | 只读，显示最终批准结果；完整操作者、时间和意见依赖 `US-017` |
| `REJECTED` | 只读，显示最终驳回结果和原因；完整结果依赖 `US-017` |

审计时间线直接嵌入详情页，不建立独立审计后台。详情与审计任一查询失败时分别显示自己的失败状态，避免审计加载失败遮挡申请主体内容。

### 5.4 编辑草稿

对应 `US-012`、`FE-012`。

- 进入页面后读取最新详情并填充完整可编辑快照。
- 保存请求携带页面读取到的 `version`，成功后使用响应中的新版本和服务端金额替换页面数据。
- `CONCURRENT_MODIFICATION` 时保留未提交表单，提示已有其他修改；用户明确确认后才能丢弃本地内容并加载服务器版本。
- `BUSINESS_CONFLICT` 表示申请已不允许编辑，页面重新读取详情并返回只读状态。
- 离开有未保存修改的页面前提供提示，但浏览器提示不能被描述为数据保护事务。

### 5.5 提交申请

对应 `US-013`、`FE-013`。

- 只在最新详情状态为 `DRAFT` 时显示提交入口。
- 提交前二次确认，展示业务编号、标题、总额和“提交后核心字段不可普通修改”的说明。
- 请求携带当前 `version` 和一次业务意图对应的 `Idempotency-Key`。
- 请求进行中禁用决定按钮；网络结果不确定时保留原键，用户重试相同载荷时复用。
- 成功后使申请详情、申请列表和相关审计 Cache 失效并重新读取服务端状态。
- `IDEMPOTENCY_IN_PROGRESS` 显示正在处理并允许稍后以同一键重试；`IDEMPOTENCY_CONFLICT` 不生成新键偷偷重发。

## 6. 审批人页面

### 6.1 审批任务列表

对应 `US-014`、`FE-014`。

- 状态筛选：全部、`PENDING`、`APPROVED`、`REJECTED`。
- URL 保存分页和筛选条件。
- 展示任务状态、任务更新时间、申请业务编号、标题、创建者、部门、交付日期和预计总额。
- 列表只使用服务端返回的已分配任务，不接受客户端传入其他受理人 ID。

### 6.2 审批任务详情

对应 `US-014`～`US-017`、`FE-014`～`FE-016`。

- 展示任务 ID、受理人、任务状态和版本，以及完整采购申请详情。
- 只有任务状态为 `PENDING` 时显示批准和驳回入口；服务端仍重新校验任务归属、申请状态、自审、版本和幂等。
- 终态任务显示已保存最终决定；刷新后恢复完整决定依赖 `US-017`。
- 审计时间线按关联申请 ID 查询并嵌入页面。

### 6.3 批准与驳回

对应 `US-015`、`FE-015`。

- 批准使用确认对话框，意见可选，最长 2000 字符。
- 驳回使用明确危险操作样式，原因必填，最长 2000 字符。
- 请求携带当前 `approvalTaskVersion` 和一次决定意图对应的 `Idempotency-Key`。
- 不做乐观 UI，不在服务端成功前把任务显示为终态。
- 成功后使任务详情、任务列表、关联申请、最终决定和审计 Cache 失效。
- `CONCURRENT_MODIFICATION` 或 `BUSINESS_CONFLICT` 后关闭决定表单并重新读取任务，显示其他请求已经改变状态；不得保留“本次已成功”的错觉。

## 7. 审计时间线

对应 `US-016`、`FE-016`。

- 使用后端给定的稳定顺序，不在浏览器重新排序。
- 展示发生时间、动作、操作者、目标类型、结果和请求标识。
- 已知动作使用中文标签；未知动作显示原始安全代码，不能导致页面崩溃。
- 不显示凭据、异常栈或不存在于白名单响应中的内部载荷。
- 不提供修改、删除、全局搜索、导出或长期归档入口。

## 8. 通用页面状态

每个异步区域必须区分：

| 状态 | UX |
| --- | --- |
| Initial Loading | 使用 Skeleton 或局部加载，避免显示错误空状态 |
| Refreshing | 保留旧内容并显示轻量刷新提示 |
| Empty | 说明为什么为空，并在角色允许时给出下一步入口 |
| Validation Error | 字段错误靠近字段，无法定位的错误显示在表单顶部 |
| Authentication Required | 清理会话并返回登录页 |
| Access Denied | 显示无权页面，不泄漏目标内容 |
| Resource Not Found | 显示不存在或不可访问，不区分无权资源 |
| Business Conflict | 说明当前业务状态已变化并重新读取资源 |
| Concurrent Modification | 保护未保存编辑并要求用户确认刷新 |
| Idempotency In Progress | 告知操作处理中，保留原幂等键 |
| Idempotency Conflict | 停止提交并显示冲突，不自动换键重试 |
| Network/Timeout | 说明无法确认结果；写操作重试必须复用原幂等键 |
| Internal Error | 显示安全通用消息和请求路径；当前 Contract 没有 `traceId` |

页面和组件不得各自解析 Axios 错误；统一映射见 `docs/API_CONTRACT.md` 与 `docs/FRONTEND_ARCHITECTURE.md`。

## 9. 可用性与可访问性

- R1 以现代桌面 Chrome/Edge 的演示体验为主，不承诺移动端产品级布局。
- 所有输入具有可见 Label，必填和错误信息不能只依赖颜色。
- 对话框打开后管理焦点；批准和驳回可用键盘完成，但危险操作不能由默认 Enter 意外确认。
- 金额以 `CNY` 格式展示，日期与 UTC 时间分别按字段语义格式化；前端不改变服务端 `LocalDate` 的日历日期。
- 状态同时使用文字，不只使用颜色图标。

## 10. R1 非范围

- 管理员后台、账号管理和角色配置。
- 生产登录、OAuth2、刷新 Token 和“记住我”。
- 材料、解析、分析、风险、建议、RAG 和 Agent 页面。
- Dashboard、全局搜索、导出、通知中心、国际化、暗色模式和移动端专项适配。
- 在页面中重建后端领域模型或绕过现有 REST API。
