# 据衡产品 Backlog

## 1. 使用方式

本 Backlog 按业务依赖排序，不代表可以并行批量实现。任何时刻只激活一个 User Story；开始前需重新检查范围、验收条件、架构影响和测试方案。

本文件负责路线、优先级、状态和依赖。近期 Story 的角色叙述、Requirement 映射和 Given/When/Then 验收条件统一记录在 `docs/USER_STORIES.md`，避免在两处维护不同版本的详细行为。

状态约定：

- `DONE`：验收条件已满足并完成验证。
- `IN_REVIEW`：文档或设计已形成，等待确认后建立基线。
- `READY`：目标和近期验收边界足够清晰，可以在确认后开始。
- `PLANNED`：方向确定，但进入开发前仍需细化验收条件。
- `GATED`：必须由前置能力或评测结果证明有必要。

优先级约定：

- `P0`：最小业务闭环或安全边界的必要能力。
- `P1`：MVP 的证据与智能增强能力。
- `P2`：由评测或运行数据驱动的优化能力。

## 3. Epic 0：项目启动文档

### DOC-000 项目启动文档

- 优先级：`P0`
- 状态：`DONE`
- 目标：建立项目范围、架构、安全决策、实施顺序和测试原则。
- 验收条件：
  - 项目上下文、产品范围、架构、Backlog、测试策略和关键 ADR 存在且职责明确。
  - 文档一致声明 LLM 不拥有最终审批或执行权限。
  - 文档明确当前阶段不实现业务代码和基础设施。
  - 内部研究资料不被当作待复制的功能清单。

### DOC-001 需求规格基线

- 优先级：`P0`
- 状态：`DONE`
- 依赖：`DOC-000`
- 目标：把产品范围转化为可编号、可验收、可追溯的功能和非功能需求。
- 验收条件：
  - 明确 R1 业务核心、R2 证据智能、R3 受约束 Agent 和 Gated 能力。
  - 覆盖角色、状态、权限、采购申请、材料、证据、风险、RAG、建议、Agent 和审计。
  - 给出业务规则、非功能要求、AI 评测指标和端到端场景。
  - 明确非目标与需要在具体 Story 前确认的事项。
  - 用户确认后将本文建立为需求基线。

### DOC-002 细化 User Stories

### DOC-003 R1 架构与领域设计

## 4. Epic 1：项目基础

### US-000 服务启动与健康检查

- 优先级：`P0`
- 状态：`READY`
- 依赖：`DOC-000`
- 用户价值：开发者能够确认服务已正确启动并检查基本存活状态。
- 验收条件：
  - 应用在明确的本地配置下可启动。
  - 健康端点返回稳定、非敏感的状态。
  - 启动测试不依赖 PostgreSQL、真实模型或额外基础设施。
  - 文档记录启动和测试命令。

### US-001 PostgreSQL 与 Flyway

- 优先级：`P0`
- 状态：`READY`
- 依赖：`US-000`
- 用户价值：后续业务数据具有可重复、可审查的 schema 演进方式。
- 验收条件：
  - 本地可启动一个当前 Story 所需的 PostgreSQL。
  - Flyway 能在空库应用基线迁移，并能重复启动而不重复执行迁移。
  - 禁止用 `ddl-auto=update` 管理 schema。
  - 集成测试使用与生产兼容的 PostgreSQL 环境并验证迁移。

### US-002 统一校验与错误响应

- 优先级：`P0`
- 状态：`READY`
- 依赖：`US-000`
- 用户价值：API 调用者能够稳定区分输入错误、权限错误、状态冲突和系统故障。
- 验收条件：
  - 定义最小错误响应结构和稳定错误代码。
  - Bean Validation 错误映射为字段级信息。
  - 业务冲突不伪装为服务器异常，内部堆栈不暴露给调用方。
  - Web 层测试覆盖代表性错误类型。

### US-003 当前用户与基础角色

- 优先级：`P0`
- 状态：`PLANNED`
- 依赖：`US-002`
- 用户价值：服务端能够从可信上下文取得当前用户及 `REQUESTER`、`APPROVER`、`ADMIN` 角色。
- 进入条件：先确认 MVP 的认证方式，不提前建设完整组织平台。
- 验收边界：
  - 业务接口不信任请求体中的用户和角色声明。
  - 未认证和无权限请求得到不同且稳定的错误。
  - 测试可显式构造不同身份，不依赖真实身份供应商。

## 5. Epic 2：采购申请与人工授权闭环

### US-010 创建采购申请草稿

- 优先级：`P0`
- 状态：`PLANNED`
- 依赖：`US-001`、`US-002`、`US-003`
- 用户价值：申请人能够保存尚未完成的采购需求。
- 验收边界：创建者来自认证上下文；字段经过校验；初始状态由服务端设置为 `DRAFT`；数据库变化使用 Flyway。

### US-011 查看自己的采购申请

- 优先级：`P0`
- 状态：`PLANNED`
- 依赖：`US-010`
- 用户价值：申请人只能查看自己有权访问的申请。
- 验收边界：单条和列表查询都包含所有权/数据范围；不存在与无权访问不泄漏额外敏感信息。

### US-012 修改采购申请草稿

- 优先级：`P0`
- 状态：`PLANNED`
- 依赖：`US-011`
- 用户价值：申请人能够在提交前修正需求。
- 验收边界：仅创建者可修改；仅 `DRAFT` 可修改受控字段；并发覆盖有明确策略和测试。

### US-013 提交采购申请

- 优先级：`P0`
- 状态：`PLANNED`
- 依赖：`US-012`
- 用户价值：申请人能够把完整草稿正式送入审批流程。
- 验收边界：服务端检查必填项、所有权和当前状态；重复提交幂等；状态变化与审计记录在同一事务中保存。

### US-014 查看待审批任务

- 优先级：`P0`
- 状态：`PLANNED`
- 依赖：`US-013`
- 用户价值：审批人只能看到分配给自己或其授权范围的任务。
- 进入条件：细化最小审批分配规则，不提前实现复杂工作流引擎。

### US-015 人工批准或驳回

- 优先级：`P0`
- 状态：`PLANNED`
- 依赖：`US-014`、`ADR-002`
- 用户价值：有权限的审批人能够明确作出最终决定。
- 验收边界：
  - 只有授权审批人可以执行，且不能通过 LLM/Agent Tool 触发。
  - 服务端校验状态、版本、输入和幂等键。
  - 决定、意见和审计记录原子保存。
  - 重复或并发决定不会产生两个成功结果。

### US-016 查看申请审计轨迹

- 优先级：`P1`
- 状态：`PLANNED`
- 依赖：`US-015`
- 用户价值：申请人和审批人能够查看自己有权访问申请的关键业务轨迹。
- 验收边界：按申请返回稳定排序的审计事件；数据范围由服务端限制；普通业务接口不能修改或删除审计事实。

## 12. Backlog 保护规则

- `PLANNED` 或 `GATED` Story 在启动前必须细化验收条件，不能直接按标题批量生成代码。
- 新基础设施必须由当前 Story 的验收条件驱动。
- 涉及授权边界、状态机、租户隔离或跨系统一致性的变化应先新增或更新 ADR。
- 研究笔记或外部参考中的功能不自动成为 Backlog。
- 完成一个 Story 后更新状态、记录偏差，再选择下一个 Story。
