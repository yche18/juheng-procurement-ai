# 据衡 R1 User Stories

- 文档状态：Baselined
- 版本：1.0
- 日期：2026-09-21
- 对应需求基线：`docs/REQUIREMENTS.md` 1.1
- 当前范围：R1 采购授权核心

## 1. 文档目的

本文把 Requirements 1.1 中的 R1 需求拆成可独立实现和验收的 User Story。每个 Story 都说明用户价值、前置条件、Requirement 追溯、Given/When/Then 验收条件、非范围和测试重点。

文档职责：

- `docs/BACKLOG.md` 管理优先级、状态、依赖和后续版本路线。
- `docs/USER_STORIES.md` 定义近期 Story 的详细行为与验收边界。
- `docs/REQUIREMENTS.md` 仍是产品需求基线；Story 不能静默改变 Requirement。

R2 证据智能和 R3 受约束 Agent 本轮不展开。完成 R1 Story 评审后，先建立 R1 领域模型，再进入实现。

## 2. R1 用户旅程

```text
已认证申请人
  -> 创建采购申请草稿
  -> 查看和修改自己的草稿
  -> 提交完整申请
  -> 系统原子创建审批任务与审计记录
  -> 被分配的审批人查看待办
  -> 审批人批准或驳回
  -> 系统原子保存最终状态、决定和审计
  -> 授权用户查看申请审计轨迹
```

R1 不接入文档解析、RAG、LLM 或 Agent。它必须在所有 AI 依赖不可用时独立成立。

## 3. 工作项类型

### 3.1 Business User Story

表达某个角色需要得到的业务结果，必须引用 Requirement ID，并使用 Given/When/Then 验收。

### 3.2 Technical Enabler

为后续 Story 提供运行、持久化或协议基础，不伪装成最终用户价值。技术前置工作继续保留在 Backlog：

| ID | 类型 | 目标 | 主要依据 | 完成后解锁 |
| --- | --- | --- | --- | --- |
| `US-000` | Enabler | 服务能够启动并提供非敏感健康检查 | Product Scope 3.1、Architecture 11 | `US-001`、`US-002` |
| `US-001` | Enabler | PostgreSQL 与 Flyway 提供可重复 schema 基线 | `NFR-COR-002`、`NFR-TST-003` | `US-010` |
| `US-002` | Enabler | API 具有统一校验和错误响应 | `FR-IAM-005`、`NFR-SEC-004` | `US-003`、所有业务 API |

这些 Enabler 仍然一次只实现一个，并遵守测试和完成报告要求；其详细技术计划在各自启动时编写。

## 4. Story 统一规则

所有 R1 Story 共同遵守：

1. 当前身份和完整角色集合来自可信认证上下文，不能信任请求体中的用户和角色。
2. 重要状态变化由服务端确定性代码执行。
3. 成功写操作产生必要审计；所有业务审计事件统一满足 `FR-AUD-003`，至少包含 actor、action、target、timestamp、result 和请求/幂等标识；失败操作不得留下部分业务状态。
4. 金额使用十进制定点语义，币种由服务端设置并只允许 `CNY`。
5. 状态、权限、重复请求和并发冲突返回可区分错误。
6. Story 未明确包含的相邻功能默认不实现。
7. 每个 Story 完成时更新 Backlog 状态和需求追溯。

## 5. US-003 当前用户与基础角色

### Story

作为 API 用户，我希望系统从可信认证信息识别我的身份和完整角色集合，以便后续业务操作能够按照真实权限执行。

### 元数据

| 字段 | 内容 |
| --- | --- |
| Release | R1 |
| Priority | P0 |
| Status | PLANNED |
| Dependencies | `US-002` |
| Requirements | `FR-IAM-001`、`FR-IAM-002`、`FR-IAM-005`、`NFR-SEC-001`、`NFR-TST-002` |

### 前置决策

- 在 Story 计划中确定 MVP 认证方式和演示账号初始化方式。
- 认证方式必须允许测试稳定构造 `REQUESTER`、`APPROVER`、`ADMIN` 身份以及同时拥有多个角色的身份。

### 验收条件

#### AC-003-01 有效身份

- Given 请求携带有效认证信息
- When 请求进入受保护接口
- Then 服务端建立包含用户 ID 和完整角色集合的可信当前用户上下文
- And 后续业务服务从该上下文取得身份

#### AC-003-02 未认证请求

- Given 请求未携带认证信息或认证信息无效
- When 请求受保护资源
- Then 返回统一的未认证错误
- And 不执行任何业务写操作

#### AC-003-03 角色不足

- Given 用户已认证但不具备目标操作所需角色
- When 请求该操作
- Then 返回统一的无权限错误
- And 不泄漏目标资源的敏感内容

#### AC-003-04 伪造身份

- Given 已认证用户在请求体、查询参数或 Header 中声明另一个 `userId` 或角色
- When 服务端处理请求
- Then 该声明不能覆盖认证上下文
- And 越权操作被拒绝

#### AC-003-05 测试身份

- Given 自动化测试不连接真实身份供应商
- When 测试构造三种角色和未认证场景
- Then 身份结果稳定、可重复且不依赖公网

#### AC-003-06 多角色身份

- Given 一个测试用户同时拥有 `REQUESTER` 和 `APPROVER` 角色
- When 请求进入受保护接口
- Then 当前用户上下文同时保留两个角色
- And 每个业务操作仍分别执行对应的角色、资源范围和职责分离校验

### 非范围

- 用户注册、密码找回和验证码。
- OAuth2 身份供应商集成。
- 组织邀请、成员申请和复杂角色继承。
- 管理角色和账号的前端页面。

### 测试重点

- 认证成功、未认证、单角色、多角色、角色不足和身份伪造。
- Controller 与 Application 层都不能从业务参数信任当前用户。

## 6. US-010 创建采购申请草稿

### Story

作为申请人，我希望创建一份采购申请草稿，以便逐步记录采购目的和采购项，再决定何时提交。

### 元数据

| 字段 | 内容 |
| --- | --- |
| Release | R1 |
| Priority | P0 |
| Status | PLANNED |
| Dependencies | `US-001`、`US-002`、`US-003` |
| Requirements | `FR-PR-001`～`FR-PR-005`、`FR-PR-010`、`FR-IAM-001`、`FR-AUD-001`、`FR-AUD-003`、`BR-001`、`BR-002` |

### 验收条件

#### AC-010-01 创建合法草稿

- Given 当前用户具有 `REQUESTER` 角色
- And 请求包含标题、采购目的、申请部门、期望交付日期和至少一个合法采购项
- When 用户创建采购申请
- Then 服务端创建状态为 `DRAFT` 的申请
- And 创建者取自认证上下文
- And 币种由服务端设置为 `CNY`
- And 返回稳定业务编号和版本信息

#### AC-010-02 采购项和金额

- Given 每个采购项包含名称、受控 `categoryCode`、规格、正数量、计量单位和非负预计单价
- When 服务端创建草稿
- Then 使用十进制定点计算每项金额及预计总额
- And 忽略或拒绝客户端试图指定的汇总金额

#### AC-010-03 非法输入

- Given 缺少必填字段、采购项为空、数量不大于零、金额非法或 `categoryCode` 不受支持
- When 用户创建草稿
- Then 返回字段级校验错误
- And 不创建申请或审计成功事件

#### AC-010-04 身份和初始状态不可伪造

- Given 请求体试图指定其他创建者、非 `CNY` 币种或非 `DRAFT` 状态
- When 服务端处理请求
- Then 客户端提供的受控字段值不得影响最终持久化结果
- And 若申请创建成功，其创建者必须是当前用户、币种必须是 `CNY`、状态必须是 `DRAFT`

#### AC-010-05 创建审计

- Given 合法草稿创建成功
- When 事务提交
- Then 保存符合第 4 节统一规则的创建审计事件
- And 申请与审计同时提交或同时回滚

### 非范围

- 上传报价或合同。
- 选择供应商和报价。
- 风险分析或审批建议。
- 采购项商品主数据维护。

### 测试重点

- 金额精度和舍入。
- 服务端受控字段。
- 事务回滚和审计一致性。

## 7. US-011 查看自己的采购申请

### Story

作为申请人，我希望分页查看自己的采购申请并打开详情，以便继续处理草稿或了解审批结果。

### 元数据

| 字段 | 内容 |
| --- | --- |
| Release | R1 |
| Priority | P0 |
| Status | PLANNED |
| Dependencies | `US-010` |
| Requirements | `FR-PR-006`、`FR-IAM-003`、`FR-IAM-005`、`NFR-SEC-002`、`NFR-PERF-001` |

### 验收条件

#### AC-011-01 分页列表

- Given 当前用户具有 `REQUESTER` 角色并拥有多份申请
- When 用户按页查询自己的申请
- Then 只返回该用户拥有的申请
- And 返回分页元数据
- And 使用稳定、可重复的排序

#### AC-011-02 状态筛选

- Given 当前用户拥有不同状态的申请
- When 用户指定合法状态筛选
- Then 只返回属于该用户且状态匹配的申请

#### AC-011-03 查看详情

- Given 当前用户是目标申请的创建者
- When 用户查看申请详情
- Then 返回申请、采购项、汇总金额、状态和版本信息

#### AC-011-04 越权详情

- Given 目标申请属于其他申请人
- When 当前用户尝试查看详情
- Then 系统不返回申请内容
- And 响应不能帮助调用者枚举其他用户资源

#### AC-011-05 非法分页或筛选

- Given 页码、每页数量或状态参数非法
- When 用户查询列表
- Then 返回统一参数校验错误
- And 不执行无界查询

### 非范围

- 审批人的任务列表。
- 全文搜索和复杂组合筛选。
- 跨组织查询和导出。

### 测试重点

- Repository 查询自身携带所有者范围。
- 分页边界、空结果和稳定排序。
- “不存在”与“无权访问”不产生敏感差异。

## 8. US-012 修改采购申请草稿

### Story

作为申请人，我希望在提交前修改自己的采购申请草稿，以便修正采购内容，同时避免覆盖他人的更新或修改已提交申请。

### 元数据

| 字段 | 内容 |
| --- | --- |
| Release | R1 |
| Priority | P0 |
| Status | PLANNED |
| Dependencies | `US-011` |
| Requirements | `FR-PR-003`～`FR-PR-005`、`FR-PR-007`、`FR-PR-011`、`FR-IAM-003`、`FR-AUD-001`、`BR-004`、`NFR-COR-003` |

### 验收条件

#### AC-012-01 修改自己的草稿

- Given 当前用户是申请创建者
- And 申请状态为 `DRAFT`
- And 请求携带当前版本
- When 用户修改允许编辑的字段或采购项
- Then 服务端重新校验字段并计算预计总额
- And 保存新版本及修改审计

#### AC-012-02 修改他人草稿

- Given 申请属于其他用户
- When 当前用户尝试修改
- Then 返回无权访问或不泄漏资源存在性的错误
- And 申请和审计均不改变

#### AC-012-03 修改非草稿

- Given 申请状态为 `SUBMITTED`、`APPROVED` 或 `REJECTED`
- When 创建者调用普通修改操作
- Then 返回业务状态冲突
- And 核心字段保持不变

#### AC-012-04 并发版本冲突

- Given 两个请求基于同一旧版本修改草稿
- When 第一个请求已经成功提交
- And 第二个请求随后提交
- Then 第二个请求得到明确并发冲突
- And 不覆盖第一个请求的结果

#### AC-012-05 修改校验失败

- Given 修改后缺少必填字段或金额/数量非法
- When 用户保存
- Then 返回字段级错误
- And 不保存部分采购项、错误总额或成功审计

### 非范围

- 提交后补证材料。
- 变更审批人。
- 申请撤销、删除和重新打开。

### 测试重点

- 所有权、状态和版本三个条件必须同时满足。
- 采购项替换/更新与汇总金额处于同一事务。

## 9. US-013 提交采购申请

### Story

作为申请人，我希望把完整草稿提交给审批人，以便正式进入人工授权流程，并确保重复点击不会创建重复任务。

### 元数据

| 字段 | 内容 |
| --- | --- |
| Release | R1 |
| Priority | P0 |
| Status | PLANNED |
| Dependencies | `US-012`、审批路由前置决策 |
| Requirements | `FR-PR-008`、`FR-PR-009`、`FR-APP-001`、`FR-APP-002`、`FR-AUD-001`、`FR-AUD-003`、`BR-003`、`BR-006`、`BR-008`、`NFR-COR-001`、`NFR-COR-003` |

### 前置决策

- 在 Story 计划中选择一个可解释的单审批人路由方式。
- 路由失败必须作为提交失败处理，不能产生没有审批任务的 `SUBMITTED` 申请。

### 验收条件

#### AC-013-01 正常提交

- Given 当前用户是完整 `DRAFT` 的创建者
- And 存在唯一可用的审批人
- And 请求携带当前版本和幂等键
- When 用户提交申请
- Then 申请转为 `SUBMITTED`
- And 创建一个分配明确、状态为 `PENDING` 的审批任务
- And 保存提交与任务创建审计
- And 上述结果在同一事务中提交

#### AC-013-02 不完整草稿

- Given 草稿缺少必填字段、没有采购项或金额不合法
- When 用户提交
- Then 返回校验错误
- And 申请保持 `DRAFT`
- And 不创建审批任务或成功审计

#### AC-013-03 非创建者提交

- Given 当前用户不是申请创建者
- When 用户提交申请
- Then 操作被拒绝
- And 申请、任务和审计均不改变

#### AC-013-04 重复提交

- Given 首次提交已经成功
- When 同一调用者使用相同幂等键和相同载荷重试
- Then 返回首次提交结果
- And 不创建第二个审批任务、状态变化或成功审计副作用

#### AC-013-05 幂等键载荷冲突

- Given 一个幂等键已经用于提交某一版本和载荷
- When 调用者使用同一键提交不同版本或不同载荷
- Then 返回幂等冲突
- And 不执行新的状态变化

#### AC-013-06 非法状态或并发修改

- Given 申请不再是 `DRAFT` 或请求版本已过期
- When 用户提交
- Then 返回状态或版本冲突
- And 不产生重复任务

#### AC-013-07 事务失败

- Given 保存审批任务或审计时发生数据库失败
- When 提交事务回滚
- Then 申请不能单独停留在 `SUBMITTED`
- And 不存在部分成功的审批任务或审计

#### AC-013-08 无法确定唯一审批人

- Given 当前申请是合法且完整的 `DRAFT`
- And 系统无法解析审批人或解析出多个候选审批人
- When 申请人提交
- Then 返回明确的审批路由错误
- And 申请保持 `DRAFT`
- And 不创建审批任务或成功提交审计

#### AC-013-09 并发相同幂等请求

- Given 同一调用者以相同幂等键、申请版本和载荷同时发起两个提交请求
- When 两个请求并发处理
- Then 最多执行一次申请状态变化、任务创建和成功审计副作用
- And 不会返回两个互相矛盾的成功结果

#### AC-013-10 审批路由命中申请人

- Given 当前申请是合法且完整的 `DRAFT`
- And 路由得到的唯一审批人就是申请创建者
- When 申请人提交
- Then 该结果被视为无有效审批路由并返回明确错误
- And 申请保持 `DRAFT`
- And 不创建审批任务或成功提交审计

### 非范围

- R2 的报价选择、材料 READY 检查和 Analysis Run。
- 多级审批、会签、加签和通用工作流。
- 申请撤回。

### 测试重点

- 幂等键绑定调用者、操作、申请和载荷，包括真正同时到达的重复请求。
- 状态、任务和审计的原子性。
- 路由失败与并发提交。

## 10. US-014 查看待审批任务

### Story

作为审批人，我希望分页查看分配给自己的审批任务并打开申请详情，以便处理自己的待办而不看到无权任务。

### 元数据

| 字段 | 内容 |
| --- | --- |
| Release | R1 |
| Priority | P0 |
| Status | PLANNED |
| Dependencies | `US-013` |
| Requirements | `FR-APP-003`、`FR-IAM-003`、`FR-IAM-005`、`NFR-SEC-002`、`NFR-PERF-001` |

### 验收条件

#### AC-014-01 分页查看自己的任务

- Given 当前用户具有 `APPROVER` 角色并被分配多个任务
- When 用户查询审批任务
- Then 只返回分配给该用户的任务
- And 返回分页元数据和稳定排序

#### AC-014-02 按状态筛选

- Given 当前审批人拥有不同状态的任务
- When 按 `PENDING`、`APPROVED` 或 `REJECTED` 筛选
- Then 只返回该审批人且状态匹配的任务

#### AC-014-03 查看任务详情

- Given 任务分配给当前审批人
- When 审批人打开任务
- Then 返回任务状态、申请摘要、申请详情、采购项和版本信息

#### AC-014-04 未分配任务

- Given 任务分配给其他审批人
- When 当前用户尝试查看
- Then 不返回任务或申请内容
- And 响应不能用于枚举其他审批人的任务

#### AC-014-05 非审批角色

- Given 当前用户不具有 `APPROVER` 角色
- When 查询审批任务
- Then 返回无权限错误

### 非范围

- R2 风险、材料、建议和补证请求展示。
- 任务转派、代办、会签和批量审批。
- 所有审批人的管理视图。

### 测试重点

- 角色与任务归属必须同时满足。
- Repository 查询直接包含 `assigneeId` 范围。

## 11. US-015 人工批准或驳回

### Story

作为被分配的审批人，我希望明确批准或驳回采购申请，以便形成唯一、可审计且不能被重复或并发请求破坏的最终决定。

### 元数据

| 字段 | 内容 |
| --- | --- |
| Release | R1 |

### 决定内容与并发版本

- 审批决定至少包含 `decision`、`actorId`、`decidedAt` 和 `comment`；`actorId` 来自可信认证上下文，`decidedAt` 由服务端生成。
- `APPROVED` 的 `comment` 可选；`REJECTED` 的 `comment` 表示驳回原因且必填。
- 审批命令由客户端携带 `approvalTaskVersion` 作为主要乐观并发版本；服务端在同一事务中同时校验任务仍为 `PENDING`、申请仍为 `SUBMITTED`，客户端不需要额外提交申请版本。

### 验收条件

#### AC-015-01 批准申请

- Given 当前用户是 `PENDING` 任务的受理审批人
- And 申请状态为 `SUBMITTED`
- And 请求携带当前 `approvalTaskVersion`、可选批准意见和幂等键
- When 审批人明确批准
- Then 任务和申请分别转为 `APPROVED`
- And 保存包含 `APPROVED`、可信 `actorId`、服务端 `decidedAt` 和可选 `comment` 的唯一审批决定及审计记录
- And 状态、决定和审计在同一事务中提交

#### AC-015-02 驳回申请

- Given 当前用户是合法受理审批人
- And 请求包含非空驳回原因、当前 `approvalTaskVersion` 和幂等键
- When 审批人明确驳回
- Then 任务和申请分别转为 `REJECTED`
- And 保存包含 `REJECTED`、可信 `actorId`、服务端 `decidedAt` 和必填 `comment` 的唯一审批决定及审计记录

#### AC-015-03 缺少驳回原因

- Given 驳回请求没有有效原因
- When 审批人提交
- Then 返回字段校验错误
- And 任务和申请保持原状态

#### AC-015-04 非受理审批人

- Given 当前用户具有 `APPROVER` 角色但任务未分配给他
- When 尝试批准或驳回
- Then 操作被拒绝
- And 不产生决定和状态变化

#### AC-015-05 申请人自审

- Given 申请创建者同时具有 `APPROVER` 角色或被错误配置为受理人
- When 尝试审批自己的申请
- Then 服务端拒绝操作
- And 记录失败所需的最小安全信息

#### AC-015-06 相同请求重试

- Given 一次审批已经成功
- When 同一调用者以相同幂等键和载荷重试
- Then 返回第一次决定
- And 不重复写入决定或成功审计副作用

#### AC-015-07 幂等键冲突

- Given 某幂等键已经用于批准
- When 使用相同键尝试驳回或改变载荷
- Then 返回幂等冲突
- And 原决定保持不变

#### AC-015-08 并发相反决定

- Given 两个请求同时基于同一 `PENDING` 任务版本
- When 一个批准、一个驳回并发提交
- Then 最多一个请求成功
- And 失败请求得到明确并发/状态冲突
- And 数据库中只有一个最终决定

#### AC-015-09 非法终态变更

- Given 任务或申请已经进入终态
- When 再次使用新幂等键尝试改变决定
- Then 返回状态冲突
- And 不覆盖原决定或审计事实

#### AC-015-10 事务失败

- Given 保存决定或审计时发生失败
- When 事务回滚
- Then 任务、申请、决定和审计不能出现部分提交

#### AC-015-11 并发相同幂等请求

- Given 同一审批人以相同幂等键、`approvalTaskVersion` 和载荷同时发起两个审批请求
- When 两个请求并发处理
- Then 最多执行一次任务状态变化、申请状态变化、决定写入和成功审计副作用
- And 不会形成两条审批决定或两个互相矛盾的成功结果

### 非范围

- R2 的补证请求和分析版本快照。
- 撤销、重新打开或修改最终决定。
- LLM/Agent 触发审批。
- 预算扣减、订单创建和付款。

### 测试重点

- 任务归属、自审禁止、`approvalTaskVersion` 和幂等校验顺序。
- 相同幂等请求顺序重试和真正并发到达时都最多产生一次业务副作用。
- 并发条件更新最多一个成功。
- 最终状态、决定和审计原子一致。

## 12. US-016 查看申请审计轨迹

### Story

作为申请人或审批人，我希望查看自己有权访问申请的审计轨迹，以便理解申请由谁在何时执行了哪些关键操作。

### 元数据

| 字段 | 内容 |
| --- | --- |
| Release | R1 |
| Priority | P1 |
| Status | PLANNED |
| Dependencies | `US-015` |
| Requirements | `FR-AUD-001`、`FR-AUD-003`、`FR-AUD-005`、`FR-AUD-006`、`FR-IAM-003`、`NFR-SEC-002` |

### 验收条件

#### AC-016-01 申请人查看轨迹

- Given 当前用户是申请创建者
- When 查看该申请审计轨迹
- Then 返回按时间稳定排序的创建、修改、提交和最终决定事件

#### AC-016-02 审批人查看轨迹

- Given 当前用户是该申请任务的受理审批人
- When 查看审计轨迹
- Then 返回其处理申请所需的关键事件

#### AC-016-03 审计内容

- Given 任一返回的审计事件
- Then 至少包含 actor、action、target、timestamp、result 和请求/幂等标识
- And 不暴露认证凭据、密钥或内部堆栈

#### AC-016-04 越权轨迹

- Given 当前用户既不是创建者，也不是任务受理审批人
- When 查看申请审计轨迹
- Then 操作被拒绝且不返回事件内容

#### AC-016-05 审计不可变

- Given 审计事件已经保存
- When 普通业务用户调用现有 API
- Then 不存在修改或删除该事件的能力

### 非范围

- 全系统审计搜索后台。
- 审计导出、长期归档和保留策略。
- R2 材料、风险、建议和 Analysis Run 事件。

### 测试重点

- 数据范围和敏感字段过滤。
- 事件顺序稳定，普通业务接口不能修改审计事实。

## 15. Definition of Ready

一个 Story 开始实现前必须满足：

1. Requirement 映射无冲突。
2. 前置 Story 已完成。
3. 前置业务决策已确认。
4. Given/When/Then 可由自动化测试验证。
5. 权限、失败、重复、并发和审计中适用部分已有边界。
6. 非范围明确，不夹带后续 Story。
7. 文件级实施计划得到确认。

## 16. Definition of Done

一个 Story 完成必须满足：

1. 所有验收条件通过。
2. 相关 Domain、Application、Web 和 Persistence 测试按风险覆盖。
3. 权限拒绝和失败路径不会留下部分状态。
4. 相关 Flyway 迁移可从空库执行。
5. 实际测试命令和结果写入完成报告。
6. Backlog、需求追溯和必要文档同步更新。
7. 项目所有者能够解释请求链路、事务边界和主要失败路径。
