# 据衡产品范围

## 1. 文档目的

本文定义据衡 MVP 要解决的问题、明确不做的内容和分阶段交付边界。`docs/BACKLOG.md` 负责把这些能力拆成 User Story；本文不表示所有能力已经实现。

## 2. 当前阶段范围

当前阶段只完成项目启动文档：

- 项目上下文与产品范围。
- 目标架构和设计边界。
- 可执行的产品 Backlog。
- 测试策略。
- LLM 权限边界 ADR。
- 项目协作规则和实施边界。

当前阶段明确不实现数据库、业务类、前端、文档解析、RAG、Agent 或部署基础设施。进入开发阶段后，必须由用户明确指定或确认一个 User Story。

## 3. MVP 范围内

### 3.1 项目基础

- Spring Boot 服务能够启动并提供健康检查。
- PostgreSQL 作为业务数据库，Flyway 管理所有结构变化。
- API 使用统一的校验和错误响应。
- 认证身份和角色可被服务端可靠取得。

### 3.2 采购申请最小闭环

- `REQUESTER` 创建、查看和修改自己的采购申请草稿。
- 申请人提交完整申请，服务端校验当前状态并防止重复提交。
- `APPROVER` 查看授权范围内的待办和相关证据。
- 审批人明确执行批准或驳回，并填写必要意见。
- 关键状态变化保存审计记录。

### 3.3 采购材料与证据

- 上传并管理报价单、合同和采购制度等材料。
- 第一版解析可直接提取文本的 PDF 和 DOCX；Markdown 是否纳入由文档 Story 最终确认。
- 材料具有明确的上传、处理、就绪和失败状态。
- 解析失败可见并允许受控重试。
- 证据保留文件、页码、章节、条款或数据记录等定位信息。

### 3.4 制度检索与引用

- 先建立最小向量检索基线，再用评测决定是否增加关键词检索、RRF 或 Rerank。
- 检索结果受组织和业务范围限制。
- 回答或建议必须返回可验证引用；证据不足时拒绝生成强结论。

### 3.5 风险分析

- 从报价单和合同中提取结构化候选字段，并在写入业务数据前校验。
- 用确定性规则检查材料完整性、金额阈值、报价一致性等可计算风险。
- 风险项具有稳定代码、严重程度、解释和证据引用。
- LLM 可以帮助解释复杂文本或生成建议草稿，但不能覆盖规则结果。

### 3.6 受约束的采购审查 Agent

- Agent 首先只使用只读工具查询制度、供应商、预算、历史采购和合同证据。
- 身份、组织、采购申请和运行 ID 来自可信运行时上下文。
- Agent 具有最大步数、重复 Tool 调用、模型调用次数和总耗时限制。
- Agent 可以创建审批建议草稿，但不能执行审批或其他关键业务动作。

### 3.7 审批与审计

- 最终批准或驳回只能由有权限人员明确发起。
- 服务端在写入前执行认证、授权、业务状态、参数和幂等校验。
- 审计记录覆盖操作者、时间、对象、动作、结果和关联证据。

## 4. MVP 明确不包含

- LLM 或 Agent 自主批准、驳回、扣减预算、创建采购订单或付款。
- OCR、扫描件识别、印章识别和复杂表格视觉解析。
- 完整 ERP、财务、支付或电子签章集成。
- 完整模型平台、多供应商动态路由、用户自带 API Key。
- Multi-Agent、MCP、长期自治任务和复杂长期记忆。
- 完整多租户、组织邀请、成员申请和复杂角色继承。
- 分块上传、极速上传、多节点任务协调和过早的消息队列建设。
- 在没有评测数据的情况下引入 Elasticsearch、混合检索或 Rerank。
- 以聊天记录或模型 Memory 代替业务数据库中的正式事实。

## 5. 质量属性

- **可解释**：风险和建议能够追溯到材料或结构化业务记录。
- **安全**：权限由服务端校验，模型不能扩张自己的工具和数据范围。
- **确定**：状态流转、金额计算、阈值判断和幂等行为可重复验证。
- **可审计**：重要命令和结果具有不可被普通业务流程悄悄绕过的记录。
- **可恢复**：异步任务失败不会永久停留在模糊状态，允许诊断和受控重试。
- **可测试**：核心规则无需真实模型即可测试，AI 能力有固定样本和量化指标。
- **可学习**：架构和代码优先保持短调用链及清晰职责，不以平台化复杂度展示能力。

## 6. 典型 MVP 业务流程

```text
申请人创建草稿
  -> 补充采购信息和材料
  -> 服务端校验并提交
  -> 系统整理证据、识别风险、生成建议草稿
  -> 审批人查看申请、风险和引用
  -> 审批人明确批准或驳回
  -> 服务端再次校验权限和状态
  -> 保存决定与审计记录
```

AI 分析失败或证据不足时，流程必须转为“待补充/人工复核”，而不是自动放行。

## 7. 范围变更规则

出现以下情况时，应先更新本文、Backlog 或新增 ADR，再实现代码：

- 新增会改变授权边界的角色或写操作。
- 新增外部系统、基础设施或跨系统事务。
- 从文本解析扩展到 OCR 或多模态。
- 从单组织假设扩展到多租户隔离。
- 允许 Agent 使用新的写工具。
- 评测结果推动检索或模型架构发生明显变化。

任何研究笔记或参考实现都不自动扩大本产品范围；真正实施仍需要对应 User Story。
