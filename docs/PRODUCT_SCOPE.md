# 据衡产品范围

## 1. 文档目的

本文定义据衡 MVP 要解决的问题、明确不做的内容和分阶段交付边界。`docs/REQUIREMENTS.md` 将范围转化为可验收需求，`docs/BACKLOG.md` 管理 Story 路线，`docs/USER_STORIES.md` 描述近期 Story 的详细验收行为；本文不表示所有能力已经实现。

## 2. 当前阶段范围

R1 后端采购授权与审计闭环已经完成。当前阶段先完成 R1 React 前端和前后端集成，再启动 R2 证据智能：

- 将现有 R1 User Story 的用户结果交付为可操作页面，不复制另一套前端业务 Story。
- 建立前端 UX、现有 API Contract、前端架构和测试基线。
- 完成申请人创建、查看、修改、提交以及审批人查看任务、批准/驳回和审计轨迹的端到端演示。
- 前端只保存会话、缓存和未提交表单等临时状态，不保存正式业务事实。
- R1 Demo Baseline 完成后，R2 按 Backend、Frontend 与 Acceptance 同一垂直切片推进。

当前阶段不实现材料、文档解析、RAG、Agent 或额外部署基础设施。所有实现继续一次只激活一个明确任务；前端集成发现现有契约无法满足已确认用户结果时，必须先提出并评审 Contract Change，不能由页面猜测或绕过。

## 3. MVP 范围内

### 3.1 项目基础

- Spring Boot 服务能够启动并提供健康检查。
- PostgreSQL 作为业务数据库，Flyway 管理所有结构变化。
- API 使用统一的校验和错误响应。
- 认证身份和角色可被服务端可靠取得。

### 3.2 采购申请最小闭环

- `REQUESTER` 创建、查看和修改自己的采购申请草稿。
- 申请人提交完整申请，服务端校验当前状态并防止重复提交。
- `APPROVER` 查看授权范围内的待办和相关证据。
- 审批人明确执行批准或驳回，并填写必要意见。
- 关键状态变化保存审计记录。

### 3.3 R1 演示客户端

- 提供 React/TypeScript 单页应用，覆盖 R1 申请人和审批人主流程。
- 页面明确展示 Loading、Empty、失败、无权限、业务冲突和并发冲突状态。
- 前端按钮可根据可信服务端响应改善体验，但不能替代服务端授权、状态、版本和幂等校验。
- HTTP Basic 只作为 R1 本地演示认证；认证凭据仅保存在浏览器内存，不进入 Redux、持久化存储、日志或错误信息。
- 前端不重新实现服务端金额、审批、所有权或状态转换规则，正式结果以 API 响应为准。

### 3.4 采购材料与证据

- 上传并管理报价单、合同和采购制度等材料。
- 第一版解析可直接提取文本的 PDF 和 DOCX；Markdown 是否纳入由文档 Story 最终确认。
- 材料具有明确的上传、处理、就绪和失败状态。
- 解析失败可见并允许受控重试。
- 证据保留文件、页码、章节、条款或数据记录等定位信息。

### 3.5 制度检索与引用

- 先建立最小向量检索基线，再用评测决定是否增加关键词检索、RRF 或 Rerank。
- 检索结果受组织和业务范围限制。
- 回答或建议必须返回可验证引用；证据不足时拒绝生成强结论。

### 3.6 风险分析

- 从报价单和合同中提取结构化候选字段，并在写入业务数据前校验。
- 用确定性规则检查材料完整性、金额阈值、报价一致性等可计算风险。
- 风险项具有稳定代码、严重程度、解释和证据引用。
- LLM 可以帮助解释复杂文本或生成建议草稿，但不能覆盖规则结果。

### 3.7 受约束的采购审查 Agent

- Agent 首先只使用只读工具查询制度、供应商、预算、历史采购和合同证据。
- 身份、组织、采购申请和运行 ID 来自可信运行时上下文。
- Agent 具有最大步数、重复 Tool 调用、模型调用次数和总耗时限制。
- Agent 可以创建审批建议草稿，但不能执行审批或其他关键业务动作。

### 3.8 审批与审计

- 最终批准或驳回只能由有权限人员明确发起。
- 服务端在写入前执行认证、授权、业务状态、参数和幂等校验。
- 审计记录覆盖操作者、时间、对象、动作、结果和关联证据。

## 4. MVP 明确不包含

- LLM 或 Agent 自主批准、驳回、扣减预算、创建采购订单或付款。
- OCR、扫描件识别、印章识别和复杂表格视觉解析。
- 完整 ERP、财务、支付或电子签章集成。
- 完整模型平台、多供应商动态路由、用户自带 API Key。
- Multi-Agent、MCP、长期自治任务和复杂长期记忆。
- 完整多租户、组织邀请、成员申请和复杂角色继承。
- 分块上传、极速上传、多节点任务协调和过早的消息队列建设。
- 在没有评测数据的情况下引入 Elasticsearch、混合检索或 Rerank。
- 以聊天记录或模型 Memory 代替业务数据库中的正式事实。
- 完整企业级前端产品、移动端、国际化、复杂组织管理后台和生产身份平台。

## 5. 质量属性

- **可解释**：风险和建议能够追溯到材料或结构化业务记录。
- **安全**：权限由服务端校验，模型不能扩张自己的工具和数据范围。
- **确定**：状态流转、金额计算、阈值判断和幂等行为可重复验证。
- **可审计**：重要命令和结果具有不可被普通业务流程悄悄绕过的记录。
- **可恢复**：异步任务失败不会永久停留在模糊状态，允许诊断和受控重试。
- **可测试**：核心规则无需真实模型即可测试，AI 能力有固定样本和量化指标。
- **可学习**：架构和代码优先保持短调用链及清晰职责，不以平台化复杂度展示能力。

## 6. 典型 MVP 业务流程

```text
申请人创建草稿
  -> 补充采购信息和材料
  -> 服务端校验并提交
  -> 系统整理证据、识别风险、生成建议草稿
  -> 审批人查看申请、风险和引用
  -> 如证据不足，审批人请求补证，申请人追加材料并触发新版分析
  -> 审批人明确批准或驳回
  -> 服务端再次校验权限和状态
  -> 保存决定与审计记录
```

AI 分析失败或证据不足时，流程必须转为“待补充/人工复核”，而不是自动放行。

## 7. 范围变更规则

出现以下情况时，应先更新本文、Backlog 或新增 ADR，再实现代码：

- 新增会改变授权边界的角色或写操作。
- 新增外部系统、基础设施或跨系统事务。
- 从文本解析扩展到 OCR 或多模态。
- 从单组织假设扩展到多租户隔离。
- 允许 Agent 使用新的写工具。
- 评测结果推动检索或模型架构发生明显变化。

任何研究笔记或参考实现都不自动扩大本产品范围；真正实施仍需要对应 User Story。
