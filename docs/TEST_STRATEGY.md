# 据衡测试策略

## 1. 目标

测试要证明据衡在正常、失败、重复和并发请求下都保持以下不变量：

- 未授权主体不能读取或修改不属于其范围的数据。
- LLM 或 Agent 不能直接批准、驳回或执行采购。
- 重要状态变化由确定性代码控制并留下审计记录。
- 重复请求不会产生重复业务结果。
- 风险和建议能够关联真实存在、可定位的证据。
- AI 或外部依赖失败时，系统进入可解释状态，而不是错误放行。

测试数量不是目标；测试应围绕业务风险选择最小但有力的验证范围。

## 2. 总体原则

1. 确定性规则优先使用快速单元测试，不启动 Spring、不调用真实模型。
2. Controller、Application、Repository 和外部适配器分别验证自己的职责边界。
3. 只有少量关键业务流程使用端到端测试，不能用端到端测试替代分层测试。
4. 普通自动化测试必须可离线、可重复，不依赖真实 LLM API、Embedding API 或公网服务。
5. AI 输出验证结构化字段、风险代码、Tool 调用和引用，不比较整段自然语言是否逐字相同。
6. 每个重要失败路径至少有一个明确测试：权限拒绝、状态冲突、格式错误、超时、重复请求或并发竞争。
7. 测试必须验证结果和重要副作用，不能只验证 HTTP 状态码或“方法被调用过”。

## 3. 测试分层

### 3.1 Domain 单元测试

适用范围：

- 采购申请状态转换。
- 金额、比例、日期和值对象校验。
- 材料完整性和风险规则。
- 证据等级计算。
- 幂等键和领域不变量。

要求：相同输入得到相同输出；不启动 Spring；不访问数据库、文件系统或模型。

### 3.2 Application 用例测试

使用 Repository、时钟、当前用户、模型和外部系统的替身，验证：

- 用例编排顺序。
- 权限和数据范围检查。
- 业务冲突与失败映射。
- 状态变化与审计写入。
- 重复请求返回已有结果。
- 外部调用失败时不会提交错误状态。

### 3.3 Web/API 测试

验证：

- JSON 请求和响应契约。
- Bean Validation 和统一错误结构。
- 认证与角色边界。
- 不接受请求体伪造的用户、组织或角色。
- 内部异常和敏感信息不会泄漏给调用方。

Web 测试不承担数据库或完整业务规则验证。

### 3.4 Persistence 集成测试

从引入 PostgreSQL 的 Story 开始，使用一次性的、与生产版本兼容的 PostgreSQL 环境验证：

- Flyway 可在空库完整执行并通过校验。
- JPA 映射、查询范围、唯一约束和外键符合预期。
- 条件更新或乐观锁能够保护并发状态变化。
- 审计与业务状态可以在同一事务提交或回滚。

不使用 H2 代替需要 PostgreSQL 语义的测试。是否采用 Testcontainers 在 `US-001` 中决定，不在文档阶段添加依赖。

### 3.5 Adapter 契约测试

文档解析器、对象存储、Embedding、检索和模型适配器分别通过稳定端口测试：

- 输入输出映射。
- 超时与错误分类。
- 重试条件。
- 资源和敏感数据处理。
- 第三方响应发生非兼容变化时的失败方式。

### 3.6 端到端测试

只覆盖少量高价值流程：

1. 申请人创建、修改并提交采购申请。
2. 审批人查看证据并人工批准或驳回。
3. 审批人创建唯一的开放补证请求，申请人追加关联材料并触发新分析版本。
4. 材料解析失败后重试并到达明确终态。
5. 风险分析产生带引用建议，但无法自行触发审批。

端到端环境使用合成身份和合成业务数据，不调用生产账户。

## 4. 测试数据与 Fixture

- 测试数据不得包含真实个人、公司、合同、账号或银行敏感信息。
- 报价单、合同和制度材料主要通过可重复的模板生成。
- 每份用于自动化验证的测试文档必须配套一个 `expected.json`。
- 原始材料与 `expected.json` 使用稳定 case ID 关联；文件内容变化时必须同步审核期望值。
- 数据集必须包含正常、缺失、冲突、边界金额、损坏文件和不支持格式等场景。
- 时间、随机数、用户身份和外部响应应可控制，避免测试依赖当前日期或执行顺序。

建议的 Fixture 组织方式在文档 Story 中最终确认，例如：

```text
src/test/resources/fixtures/documents/<case-id>/
  source.pdf | source.docx
  expected.json
```

`expected.json` 至少描述该用例需要验证的字段、风险代码和引用定位；不得把模型生成的整段措辞作为黄金答案。

## 5. 采购状态、权限与审计测试

每个重要命令都使用正向和拒绝矩阵验证：

| 场景 | 必须验证 |
| --- | --- |
| 合法角色 + 合法状态 | 操作成功，状态和审计一致 |
| 错误角色或错误数据范围 | 拒绝且不产生写入 |
| 合法角色 + 非法状态 | 返回业务冲突，不改变数据 |
| 同一幂等键重复请求 | 不产生第二个结果或第二次副作用 |
| 不同载荷复用幂等键 | 明确拒绝冲突 |
| 两个审批人并发决定 | 最多一个成功，失败方得到清晰冲突 |
| 事务中途失败 | 状态与审计同时回滚 |
| `SUBMITTED` 追加补充材料 | 仅存在所属任务的 `OPEN` 补证请求时允许新增关联材料；拒绝主动追加、删除、覆盖或修改核心字段 |
| 补证响应后重新分析 | 创建新 Analysis Run，旧运行、风险和建议仍可追溯 |
| 开放补证时执行最终审批 | 拒绝审批；取消请求需原因，取消后才允许继续决定 |
| 并发创建补证请求 | 同一任务最多一个 `OPEN` 请求 |
| 激活同一制度的新版本 | 同时最多一个 `ACTIVE`，历史运行仍引用旧版本 |
| 历史价格可比性 | 只使用相同 `categoryCode` 和计量单位的记录，报价明细未映射时不运行确定性价格偏差规则 |

特别验证申请人不能审批自己的申请、请求体不能伪造审批人，以及删除/修改普通业务数据不能悄悄抹去审计事实。

## 6. 文档处理测试

### 6.1 解析

- 支持的文本型 PDF/DOCX 能提取预期字段和定位信息。
- 空文件、加密文件、损坏文件、不支持类型和扩展名伪装得到明确错误。
- 第一版测试明确证明扫描件不会被误报为成功解析。
- 文件名、内容类型、大小和存储键得到校验。

### 6.2 生命周期与异步

验证状态路径：

```text
UPLOADED -> PROCESSING -> READY
                       -> FAILED
```

同时覆盖：

- 数据库事务未提交时不启动处理。
- 同一材料被重复投递时不会生成重复结果。
- 暂时性错误按预算重试，确定性校验错误不重试。
- 新近任务不会被恢复逻辑误判，真正超时任务可以恢复或进入失败。
- 服务重启或任务丢失的已知限制有测试或可操作的人工恢复路径。

## 7. AI 结构化输出测试

普通测试使用固定假的模型响应，覆盖：

- 完整合法 JSON。
- 缺少必填字段。
- 未知枚举和额外字段。
- 金额、比例或日期越界。
- 引用不存在或指向无权访问材料。
- 模型返回自然语言、Markdown 代码块或无法解析内容。
- 超时、限流和供应商错误。
- 模型试图把“建议”伪装成“已批准”。

业务型解析失败不得回退为把原始模型文本直接写入领域表。测试应断言失败结果、人工复核状态或重新提取路径，而不是仅断言记录了日志。

Recommendation 生成或校验失败时，还必须断言所属 Analysis Run、Evidence 和确定性 Risk 保持成功结果，审批界面/API 能明确区分“分析完成但建议失败”。

## 8. RAG 评测

在实现检索前先建立固定评测集，每个问题至少包含：

- 问题和业务范围。
- 预期命中的文档版本、章节、页码或 chunk。
- 可接受的替代证据。
- 在证据不足时应拒答的标记。

基线指标包括：

- `Recall@K`：预期证据是否出现在前 K 个候选中。
- 证据覆盖率：回答所需关键依据是否齐全。
- 引用准确率：引用是否真实支持对应结论。
- 越界检索率：是否返回其他组织或无权材料，目标必须为零。
- 无依据强答率：没有充分证据时仍给出确定结论的比例，目标必须持续压低。

只有对照评测证明有收益后，才能用 BM25、RRF、Rerank 或查询改写替换/扩充基线。参数必须通过据衡自己的数据集确定，不能直接沿用外部示例常量。

## 9. Agent 测试

Agent 测试使用假的模型响应和可观察的 Tool 替身，验证：

- 只注册当前模式允许的 Tool。
- 用户、组织、采购申请和 Agent Run 范围来自可信 `ToolContext`。
- 模型传入其他用户或组织 ID 时被忽略或拒绝。
- 同一 Tool 的重复调用受限。
- 最大步数、模型调用次数和总耗时预算生效。
- Tool 异常、超时和部分结果得到明确处理。
- Agent 只能创建审批建议草稿，不能调用批准、驳回、订单或付款能力。
- Prompt Injection、伪造引用和越权指令不会绕过服务端规则。

Agent 轨迹测试关注允许的 Tool、参数边界、调用顺序、最终结构和终止原因，不锁定模型生成的每个自然语言 Token。

## 10. 在线模型评测

真实模型测试与常规构建分离：

- 只在显式启用且凭据可用的环境运行。
- 不作为普通单元测试失败的随机来源。
- 记录模型、版本、Prompt 版本、参数、数据集版本和评测时间。
- 使用脱敏或合成数据，不向外部模型发送生产合同和个人信息。
- 报告多次运行的波动，不以单次演示作为质量结论。
- 保留一组不参与 Prompt 调试的隐藏评测集，用于发现过拟合。

在线评测通过不代表模型获得业务授权；权限边界仍由确定性测试保证。

## 11. CI 门禁

随着能力逐步引入，CI 至少执行：

1. 编译和静态检查。
2. Domain 与 Application 单元测试。
3. Web/API 测试。
4. PostgreSQL/Flyway 集成测试。
5. 固定 Fixture 的文档、RAG 和 Agent 离线回归。

真实模型评测、长时间性能测试和隐藏集评测可以独立运行，但发布候选版本必须查看其结果。任何失败测试不得仅通过放宽断言或删除边界用例来恢复绿色。

## 12. Story 的测试完成标准

每个 Story 完成报告必须列出：

- 新增或修改了哪些行为。
- 正常、失败、权限、重复和并发场景中哪些适用并已覆盖。
- 实际执行的测试命令及结果。
- 未执行的测试及原因。
- 仍依赖人工验证或真实外部服务的风险。

纯文档 Story 不要求启动无关基础设施，但必须检查文件存在、Markdown 结构、相对链接和跨文档范围是否一致。
