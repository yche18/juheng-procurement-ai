# 据衡项目上下文

## 1. 项目定位

据衡（Juheng）是一个企业采购证据决策与授权平台。

系统围绕采购申请，收集报价单、采购制度、供应商档案、历史价格和合同等证据，识别材料缺失、价格异常、制度冲突和合同风险，并生成带依据的审批建议。建议用于辅助有权限的人员决策，不替代最终审批，也不直接触发采购执行或付款。

据衡要解决的核心问题不是“让模型替人批准”，而是让审批人更快看清：

- 这次采购要买什么、为什么买、金额是多少。
- 关键材料是否齐全，材料之间是否一致。
- 哪些制度和历史数据适用于当前申请。
- 存在哪些风险，每项风险由什么证据支持。
- 在证据不足或冲突时，下一步应补充什么或由谁复核。

## 2. 目标用户

MVP 采用最小角色模型：

| 角色 | 主要职责 | 权限边界 |
| --- | --- | --- |
| `REQUESTER` | 创建、修改并提交自己的采购申请和材料 | 不能审批自己的申请，不能修改已提交申请的受控字段 |
| `APPROVER` | 查看分配给自己的审批任务、证据和风险，并作出人工决定 | 只能处理授权范围内的任务，不能把模型建议当作已执行决定 |
| `ADMIN` | 维护必要的系统配置并处理受控运维事项 | 管理权限不等于业务审批意见，敏感操作仍需审计 |

完整组织管理、多租户模型和复杂角色继承不属于当前 MVP；出现明确需求时再通过独立 Story 和 ADR 设计。

## 3. 业务输入与产出

### 3.1 证据输入

- 采购申请：需求描述、品类、数量、预算、申请部门等结构化事实。
- 报价单：供应商、单价、总价、税费、交付和付款条件。
- 采购制度：审批阈值、询比价要求、例外条件和授权规则。
- 供应商档案：基本资质、状态和已知风险信息。
- 历史价格：相同或相近物品的历史成交记录。
- 合同：金额、标的、交付、付款、违约和终止条款。

输入材料可能缺失、过期、相互矛盾或解析失败。系统不得默认输入天然正确。

### 3.2 系统产出

- 可追溯的结构化证据。
- 材料完整性和冲突提示。
- 由确定性规则识别的风险项。
- 由 LLM 辅助生成、经过校验的解释和审批建议草稿。
- 对应原文件、页码、章节或数据记录的证据引用。
- 人工作出的批准或驳回结果及完整审计记录。

## 4. 决策权边界

| 能力 | LLM | 确定性服务端代码 | 有权限的人员 |
| --- | --- | --- | --- |
| 从材料中提取候选字段 | 可以 | 校验并决定是否接纳 | 必要时复核 |
| 解释证据、生成摘要 | 可以 | 限制输入输出并保存溯源 | 阅读和判断 |
| 识别确定性阈值风险 | 可辅助解释 | 最终计算和判定 | 复核 |
| 生成审批建议或草稿 | 可以 | 校验、标记为建议 | 接受、修改或忽略 |
| 批准、驳回采购 | 不可以 | 校验权限和状态、执行命令 | 作出明确决定 |
| 扣减预算、创建采购订单、付款 | 不可以 | 仅在未来明确授权流程中执行 | 按企业制度授权 |

详细约束见 `docs/adr/ADR-002-llm-cannot-directly-approve.md`。

## 5. 核心原则

1. **证据优先**：结论必须尽可能关联来源；无法定位来源时，应降低结论强度。
2. **职责分离**：AI 擅长提取和解释，Java 规则负责状态、权限、金额和阈值等确定性判断。
3. **人工授权**：LLM 只能提出建议或动作草稿，不能直接完成重要业务操作。
4. **服务端控制**：关键状态变化、身份范围、幂等和审计均由服务端强制执行。
5. **显式不确定性**：证据缺失、冲突或模型失败必须成为可见状态，不能用流畅文本掩盖。
6. **增量交付**：采用垂直切片，每个 Story 都应形成可理解、可测试的小闭环。
7. **按需引入复杂度**：没有当前需求和评测证据时，不提前引入高级检索、消息队列或平台化能力。
8. **独立演进**：只引入当前业务需要且能够验证的机制，不照搬外部项目结构或预先建设平台能力。

## 6. 当前约束

- 当前仓库已经完成 R1 Spring Boot 后端，目标运行时使用 Java 17；当前阶段为 R1 React 前端与前后端集成。
- R1 前端只交付可复现、可演示的采购授权闭环，不建设完整企业管理后台，也不改变服务端作为业务事实、权限和状态判断最终来源的边界。
- R1 前端使用 React、TypeScript、Vite、React Router、Ant Design、Axios、Redux Toolkit 和 RTK Query；依赖只在当前任务实际需要时加入。
- 文档处理第一版面向可直接提取文本的 PDF 和 DOCX；采购制度可在对应 Story 中确认是否增加 Markdown。
- 第一版不实现 OCR、印章识别、扫描件解析和复杂表格视觉理解。
- 对象存储、向量检索和模型服务只在对应 R2/R3 Story 到来时按需引入。
- 业务数据库是事实源；模型输出、聊天记录和 Agent Memory 都不是业务事实源。

## 7. 成功标准

据衡的首要成功标准是完成一个可信的采购闭环，而不是堆叠 AI 功能：

1. 申请人可以创建并提交采购申请。
2. 系统能够组织相关证据并明确材料缺口。
3. 风险项具有稳定代码、可理解解释和可定位引用。
4. 审批人能够基于证据作出人工决定。
5. 权限、状态变化、重复请求和失败路径可预测。
6. 关键操作能够回答“谁在何时基于什么做了什么”。
7. AI 能力通过固定评测集证明价值，并且失败时不会越权改变业务状态。

## 8. 术语

- **证据（Evidence）**：支持或反驳某项业务事实、风险或建议的可定位信息。
- **风险项（Risk Item）**：具有稳定风险代码、严重程度、解释、状态和证据引用的结构化记录。
- **审批建议（Approval Recommendation）**：供审批人参考的草稿，不是审批结果。
- **审批决定（Approval Decision）**：由有权限人员明确发起、经服务端校验后形成的业务状态变化。
- **确定性规则（Deterministic Rule）**：相同输入必然得到相同结果的业务判断，例如金额阈值和必填材料检查。
- **证据等级（Evidence Level）**：综合完整性、相关性、一致性和数据来源得到的证据充分程度，不等同于模型自报置信度。
