## 1. 文档目的

本文把产品范围转化为可编号、可验收、可追溯的需求，作为后续 User Story、领域模型、API、数据库设计和测试用例的共同输入。

本文回答“系统必须做什么以及做到什么程度”，不提前规定 Controller、Entity、表结构或框架写法。需求实现仍按 `docs/BACKLOG.md` 一次推进一个 User Story。

文档关系：

- `docs/PROJECT_CONTEXT.md`：解释项目为什么存在。
- `docs/PRODUCT_SCOPE.md`：定义 MVP 边界和非目标。
- `docs/REQUIREMENTS.md`：定义可验收的产品需求。
- `docs/BACKLOG.md`：把需求拆成可交付的 User Story。
- `docs/USER_STORIES.md`：定义近期 Story 的详细行为和验收条件。
- `docs/ARCHITECTURE.md`：约束系统边界和依赖方向。
- `docs/adr/`：记录不可轻易改变的重要决策。
- `docs/TEST_STRATEGY.md`：定义如何验证需求。

如本文与已接受 ADR 冲突，以 ADR 为准；如需求需要扩大产品范围，应先更新 `PRODUCT_SCOPE.md`。

本版本建立后，需求语义变化必须记录变更原因、影响的 Requirement ID、User Story 和测试；不能在实现过程中静默改变 Baseline。

1.1 相对 1.0 的澄清：`FR-IAM-002` 明确单个用户可同时拥有多个角色；`FR-PR-004` 明确预计单价不得为负；`FR-PR-010` 将稳定业务编号确认为 R1 必需能力；`FR-APP-001` 明确审批任务不得分配给申请创建者。这些调整分别影响 `US-003`、`US-010`、`US-013` 及其权限、字段校验和路由测试，不引入新的产品模块。

## 2. 产品目标

据衡要完成一个“证据驱动的采购申请与人工授权闭环”：

1. 申请人提交结构化采购需求和相关材料。
2. 系统从报价、合同、制度、供应商和历史价格中组织证据。
3. 确定性规则识别可计算风险。
4. RAG 和 LLM 对复杂文本进行检索、提取和解释，形成带引用的建议草稿。
5. 审批人查看事实、风险、缺失项和引用后作出人工决定。
6. 服务端保证权限、状态、幂等、并发和审计边界。

项目不追求模拟完整采购 ERP，而是把上述单一闭环做完整、可测试、可演示和可解释。

## 3. 交付层次

### 3.1 R1：采购授权核心

目标是证明 Java 后端业务能力，不依赖 LLM：

- PostgreSQL 与 Flyway。
- 当前用户和最小角色权限。
- 采购申请草稿、提交和查询。
- 单级人工审批、驳回和审计。
- 幂等提交、并发审批保护和统一错误响应。

### 3.2 R2：证据智能

目标是形成据衡的业务差异：

- 报价单、合同和采购制度的文本型 PDF/DOCX 处理。
- 结构化字段提取及人工可复核结果。
- 供应商档案和基于稳定品类编码的历史价格查询。
- 明确选定报价与候选供应商，并允许提交后的受控补证。
- 采购制度 RAG、证据等级和可定位引用。
- 确定性风险规则和结构化审批建议草稿。
- 固定数据集、失败归因和离线评测。

### 3.3 R3：受约束采购审查 Agent

目标是展示受控 Tool Calling，而不是自主审批：

- Agent Run 和 Tool Call 记录。
- 只读采购 Tool。
- 可信运行时上下文。
- 重复调用、最大步数、模型次数和超时预算。
- 生成审批建议草稿。
- 越权、Prompt Injection 和失败降级测试。

### 3.4 Gated：评测后才允许进入

- Elasticsearch/BM25、RRF 和 Rerank。
- Query Rewrite/Decompose。
- SSE 流式进度。
- Outbox、MQ 或多节点任务协调。
- Redis 缓存。
- OCR、多模态和复杂表格解析。

这些能力只有在基线评测或运行问题证明有必要时才进入 Backlog。

## 4. 角色与外部参与者

| 参与者 | 目标 | 主要权限 |
| --- | --- | --- |
| `REQUESTER` | 创建采购需求、上传材料并提交审批 | 管理自己的草稿，查看自己的申请及处理结果 |
| `APPROVER` | 基于证据和风险作出人工决定 | 查看分配给自己的任务，批准或驳回 |
| `ADMIN` | 维护演示所需的制度和基础参考数据 | 管理制度版本和受控配置，不自动获得业务审批权 |
| 系统任务 | 解析材料、运行规则、生成分析结果 | 只能在服务端预定义范围内改变处理状态 |
| LLM/Agent | 提取、检索、解释和形成建议草稿 | 不拥有用户身份、审批权或执行权 |

MVP 使用单组织假设。部门 ID 用于数据和规则上下文，但不建设完整组织树、租户平台或成员邀请流程。

## 5. 核心业务流程

```text
REQUESTER 创建 DRAFT
  -> 填写采购项和预算
  -> 上传报价/合同草案并选择拟采购供应商及报价
  -> 查看材料处理和字段提取结果
  -> 提交申请
  -> 系统创建 PENDING 审批任务
  -> 系统创建 Analysis Run，等待本次材料快照处理完成
  -> Analysis Run 整理可用证据并运行确定性规则
  -> Recommendation 独立生成带引用的建议草稿
  -> APPROVER 查看申请、风险、缺失项和引用
  -> APPROVER 明确批准或驳回
  -> 服务端校验权限、状态、版本和幂等键
  -> 保存最终决定与审计记录
```

AI 分析可以在提交后异步完成。AI 失败不得阻塞审批人查看申请和作出人工决定，但页面/API 必须明确显示分析未完成或失败，不能伪装成“无风险”。

证据不足时使用不改变采购申请状态的补证支路：

```text
APPROVER 在 PENDING 任务上发起补证请求
  -> REQUESTER 在 SUBMITTED 申请中追加材料
  -> REQUESTER 提交补证响应
  -> 系统创建新的 Analysis Run
  -> APPROVER 查看新旧分析版本后继续决定
```

补证只允许追加材料，不允许覆盖原材料或修改已提交的核心申请字段。

## 6. 状态要求

不同职责使用独立状态，禁止用一个巨大状态枚举同时表示采购、文件和 AI 任务。

### 6.1 采购申请状态

```text
DRAFT -> SUBMITTED -> APPROVED
                   -> REJECTED
```

- `DRAFT`：申请人可编辑受控字段和材料。
- `SUBMITTED`：等待人工决定；核心申请内容不可修改，只有存在当前任务的 `OPEN` 补证请求时才允许追加与请求关联的材料。
- `APPROVED`、`REJECTED`：终态，MVP 不提供撤销和重新打开。

### 6.2 审批任务状态

```text
PENDING -> APPROVED
        -> REJECTED
```

审批任务状态与采购申请状态必须保持业务一致，但分别承担“待办归属”和“申请最终结果”的职责。

### 6.3 材料状态

```text
UPLOADED -> PROCESSING -> READY
                       -> FAILED
```

### 6.4 分析运行状态

```text
PENDING -> RUNNING -> COMPLETED
                   -> FAILED
```

分析失败不是采购申请的批准或驳回状态。

### 6.5 Recommendation 状态

```text
PENDING -> RUNNING -> COMPLETED
                   -> FAILED
```

Recommendation 是 Analysis Run 的子结果，但状态独立。Evidence 和确定性 Risk 已成功产生时，Recommendation 生成或校验失败不得把已完成的 Analysis Run 改为 `FAILED`。

### 6.6 补证请求状态

```text
OPEN -> RESPONDED
     -> CANCELLED
```

补证请求是审批任务中的协作记录，不改变采购申请的 `SUBMITTED` 或审批任务的 `PENDING` 状态。一次申请可以有多轮补证，但同一审批任务同时最多一个 `OPEN` 请求，每次请求、响应和取消必须独立留痕。

## 7. 功能需求

优先级说明：

- `MUST`：对应版本不可缺少。
- `SHOULD`：显著提升完整性，但可在该版本末尾交付。
- `GATED`：满足明确进入条件后再实现。

### 7.1 身份与授权

| ID | 优先级 | 需求 |
| --- | --- | --- |
| FR-IAM-001 | R1 MUST | 系统必须从可信认证上下文取得当前用户，不能采用请求体声明的 `userId` 作为当前身份。 |
| FR-IAM-002 | R1 MUST | 系统必须支持 `REQUESTER`、`APPROVER`、`ADMIN` 三种最小角色；同一用户可以同时拥有一个或多个角色，可信认证上下文必须提供完整角色集合。 |
| FR-IAM-003 | R1 MUST | 申请查询和修改必须校验所有权或审批任务范围，不能只依赖前端隐藏按钮。 |
| FR-IAM-004 | R1 MUST | 申请人不得审批自己的采购申请。 |
| FR-IAM-005 | R1 MUST | 未认证、无角色、无数据权限和业务状态冲突必须返回可区分的错误。 |
| FR-IAM-006 | R2 MUST | 材料、证据、风险、检索结果和分析运行必须继承所属申请或制度库的数据范围。 |

### 7.2 采购申请

| ID | 优先级 | 需求 |
| --- | --- | --- |
| FR-PR-001 | R1 MUST | `REQUESTER` 必须能够创建采购申请草稿，创建者和初始状态由服务端设置。 |
| FR-PR-002 | R1 MUST | 草稿至少包含标题、采购目的、申请部门、期望交付日期和一个采购项；币种字段由服务端默认设置。 |
| FR-PR-003 | R1 MUST | 采购项至少包含名称、稳定 `categoryCode`、规格说明、数量、计量单位和预计单价；MVP 使用受控的合成品类编码，不建设商品主数据系统。 |
| FR-PR-004 | R1 MUST | 数量必须大于零，预计单价不得为负，金额使用十进制定点数；币种字段保留，但 R1/R2 仅允许 `CNY`，由服务端默认并校验，金额保留两位小数。 |
| FR-PR-005 | R1 MUST | 预计总额由服务端根据采购项计算，不能信任客户端传入的汇总金额。 |
| FR-PR-006 | R1 MUST | 创建者必须能够分页查看自己的申请，并按状态筛选。 |
| FR-PR-007 | R1 MUST | 只有创建者能够修改自己的 `DRAFT`；`SUBMITTED` 及终态申请不得通过普通修改接口改变核心字段。 |
| FR-PR-008 | R1 MUST | 提交时必须重新校验必填字段、采购项、金额、所有权和当前状态；R2 中引用材料只需确认原文件已可靠保存并完成登记，不要求解析状态为 `READY`。 |
| FR-PR-009 | R1 MUST | 提交操作必须支持幂等键；相同调用者、申请和载荷的重复请求不得创建第二次提交结果。 |
| FR-PR-010 | R1 MUST | 系统必须为已创建申请生成稳定、可展示的业务编号。 |
| FR-PR-011 | R1 MUST | 更新操作必须使用版本或条件更新发现并发覆盖。 |
| FR-PR-012 | R2 MUST | 启用 R2 后，采购申请提交前必须关联一个拟采购供应商和一份选定报价材料；选定报价必须属于当前申请、类型为报价单，且其声明供应商与拟采购供应商一致。 |

### 7.3 审批任务与决定

| ID | 优先级 | 需求 |
| --- | --- | --- |
| FR-APP-001 | R1 MUST | 成功提交申请后，系统必须按最小路由规则创建一个 `PENDING` 审批任务；任务受理审批人不得是申请创建者。 |
| FR-APP-002 | R1 MUST | MVP 采用单级审批和单一受理审批人，不引入 BPM 或通用工作流引擎。 |
| FR-APP-003 | R1 MUST | `APPROVER` 能够分页查看分配给自己的审批任务并按状态筛选，且只能查看和处理自己授权范围内的任务。 |
| FR-APP-004 | R1 MUST | 审批人必须通过独立命令明确批准或驳回；驳回必须填写原因。 |
| FR-APP-005 | R1 MUST | 批准/驳回必须校验角色、任务归属、申请状态、任务状态、版本和幂等键。 |
| FR-APP-006 | R1 MUST | 并发审批最多一个成功，失败方获得明确的状态冲突。 |
| FR-APP-007 | R1 MUST | 申请状态、任务状态、审批决定和审计记录必须在同一数据库事务中提交。 |
| FR-APP-008 | R2 MUST | 审批页面/API 必须区分“未发现风险”“分析未完成”“分析失败”和“证据不足”。 |
| FR-APP-009 | R2 MUST | 即使 AI 分析不可用，审批人仍可基于原始申请和材料人工处理，并在审计中保留当时的分析状态。 |
| FR-APP-010 | R2 MUST | 审批决定必须保存当时所查看的 Analysis Run、风险项和建议版本引用，避免后续重跑分析改变历史解释。 |
| FR-APP-011 | R2 MUST | `APPROVER` 可以在 `PENDING` 任务上发起补证请求，填写原因和所需材料说明；申请和任务状态保持不变，请求对申请人可见并写入审计。 |
| FR-APP-012 | R2 MUST | 申请人可以查看未完成补证请求，把新增材料关联到请求并提交补证响应；补证请求使用 `OPEN`、`RESPONDED`、`CANCELLED` 状态。 |
| FR-APP-013 | R2 MUST | 只有当前任务的受理审批人能够取消 `OPEN` 补证请求；取消必须填写原因并将请求转为 `CANCELLED`。 |
| FR-APP-014 | R2 MUST | 同一审批任务同时最多存在一个 `OPEN` 补证请求；存在 `OPEN` 请求时不得批准或驳回，审批人必须先等待响应或取消请求。 |

### 7.4 采购材料

| ID | 优先级 | 需求 |
| --- | --- | --- |
| FR-MAT-001 | R2 MUST | 申请人能够为自己的 `DRAFT` 上传报价单和合同草案；上传报价单时必须声明其候选供应商。 |
| FR-MAT-002 | R2 MUST | `ADMIN` 能够上传采购制度，并记录制度名称、版本和生效状态。 |
| FR-MAT-003 | R2 MUST | MVP 支持可直接提取文本的 PDF 和 DOCX；扫描件和复杂视觉表格必须明确标记为不支持或解析失败。 |
| FR-MAT-004 | R2 MUST | 上传必须校验材料类型、内容类型、大小、文件名和存储对象键；大小上限必须可配置。 |
| FR-MAT-005 | R2 MUST | 材料记录至少保存所属范围、材料类型、原文件名、内容类型、存储键、状态、失败原因和时间信息。 |
| FR-MAT-006 | R2 MUST | 文件可靠保存并登记为 `UPLOADED` 后，才能在事务提交后启动异步解析。 |
| FR-MAT-007 | R2 MUST | 异步解析必须以材料 ID 作为输入，并以 `READY` 或 `FAILED` 结束；不得跨线程依赖原事务实体。 |
| FR-MAT-008 | R2 MUST | 同一材料任务重复投递不得生成重复解析结果。 |
| FR-MAT-009 | R2 SHOULD | 授权用户可以对 `FAILED` 材料发起受控重试，并查看最近一次失败原因。 |
| FR-MAT-010 | R2 SHOULD | 超时恢复只能处理超过配置阈值的 `PROCESSING` 任务，不能误伤新近任务。 |
| FR-MAT-011 | R2 MUST | 申请提交后，关联材料不可被无痕替换；需要变更时必须形成新版本或新的受控流程。 |
| FR-MAT-012 | R2 MUST | 当申请为 `SUBMITTED` 时，只有存在属于当前申请和审批任务的 `OPEN` 补证请求，创建者才能追加材料；新增材料必须关联该请求，且不能删除、替换旧材料或修改核心申请字段，追加动作必须审计。 |

### 7.5 基础参考数据

| ID | 优先级 | 需求 |
| --- | --- | --- |
| FR-REF-001 | R2 MUST | 系统能够读取供应商档案，至少包含供应商 ID、名称、统一标识、状态和风险标签。 |
| FR-REF-002 | R2 MUST | 供应商状态至少区分正常、暂停合作和禁用；非正常状态必须形成确定性风险。 |
| FR-REF-003 | R2 MUST | 系统能够按稳定 `categoryCode` 查询历史采购记录，至少返回供应商、成交单价、数量、计量单位、币种和成交日期。 |
| FR-REF-004 | R2 SHOULD | 演示数据通过合成数据集导入，不为 MVP 建设完整供应商主数据管理界面。 |

### 7.6 字段提取与证据

| ID | 优先级 | 需求 |
| --- | --- | --- |
| FR-EVD-001 | R2 MUST | 报价单提取候选结果至少覆盖供应商、报价日期、币种、明细、税费、总价、交付和付款条件。 |
| FR-EVD-002 | R2 MUST | 合同提取候选结果至少覆盖合同主体、金额、币种、交付、付款、预付款比例和关键违约条款。 |
| FR-EVD-003 | R2 MUST | 模型输出必须先映射到白名单 DTO，再执行 Schema、类型、枚举、范围、业务对象和引用校验。 |
| FR-EVD-004 | R2 MUST | 每个进入分析的关键字段必须标明来源类型、来源 ID 和可用的页码、章节、条款或范围。 |
| FR-EVD-005 | R2 MUST | 无法定位来源的模型文本不能成为已验证业务事实。 |
| FR-EVD-006 | R2 SHOULD | 授权用户可以修正候选字段；系统必须保留原提取值、修正值、操作者和时间。 |
| FR-EVD-007 | R2 MUST | 证据充分程度使用 `NONE`、`WEAK`、`PARTIAL`、`SUFFICIENT`，且不能仅由 LLM 自报置信度决定。 |
| FR-EVD-008 | R2 MUST | 证据等级必须综合必填字段完整性、检索结果、规则命中、数据查询成功和材料冲突情况。 |
| FR-EVD-009 | R2 MUST | 选定报价中用于确定性价格规则的明细必须显式映射到对应 `ProcurementItem`；模型可以提出候选映射，但映射必须通过服务端校验或人工确认后才能参与规则计算。 |

### 7.7 确定性风险规则

| ID | 优先级 | 需求 |
| --- | --- | --- |
| FR-RISK-001 | R2 MUST | 相同输入、规则版本和配置必须产生相同的风险结果。 |
| FR-RISK-002 | R2 MUST | 风险项必须包含稳定风险代码、严重程度、标题、解释、规则版本、分析运行和证据引用。 |
| FR-RISK-003 | R2 MUST | 阈值来自版本化配置或样例制度，不在代码中散落魔法数字，也不声明为通用法律标准。 |
| FR-RISK-004 | R2 MUST | 规则引擎必须至少覆盖材料不足、报价金额不一致、历史价格异常、供应商状态异常、合同金额不一致和高预付款六类风险。 |
| FR-RISK-005 | R2 MUST | LLM 可以解释风险，但不得覆盖、删除或修改确定性规则的命中结果。 |
| FR-RISK-006 | R2 SHOULD | 重新分析产生新的运行版本；历史审批引用的旧结果仍可追溯。 |

首批风险代码：

| 风险代码 | 条件摘要 | 主要证据 |
| --- | --- | --- |
| `MISSING_REQUIRED_QUOTATION` | 按适用制度要求，报价数量不足 | 申请金额、报价材料、制度条款 |
| `QUOTATION_TOTAL_MISMATCH` | 报价总价与明细计算不一致 | 报价字段及原文位置 |
| `HISTORICAL_PRICE_DEVIATION` | 映射后的选定报价明细显著高于同 `categoryCode`、同计量单位的可比历史价格 | 采购项、报价明细映射、历史成交记录、阈值配置 |
| `SUPPLIER_STATUS_RISK` | 供应商处于暂停合作或禁用状态 | 供应商档案 |
| `CONTRACT_AMOUNT_MISMATCH` | 合同金额与选定报价或申请金额不一致 | 申请、报价和合同证据 |
| `HIGH_PREPAYMENT_RATIO` | 预付款比例超过适用制度阈值 | 合同条款和制度条款 |

### 7.8 采购制度版本

| ID | 优先级 | 需求 |
| --- | --- | --- |
| FR-POL-001 | R2 MUST | 每类制度使用稳定 `policyKey` 标识，制度内容以不可覆盖的 `PolicyVersion` 保存。 |
| FR-POL-002 | R2 MUST | 同一 `policyKey` 在同一适用范围内同时最多存在一个 `ACTIVE` 版本；激活新版时旧版原子转为 `RETIRED`。 |
| FR-POL-003 | R2 MUST | `RETIRED` 版本不进入新的默认检索，但不得因停用而删除，历史分析仍可读取并引用。 |
| FR-POL-004 | R2 MUST | Analysis Run 必须保存执行时实际使用的 PolicyVersion 集合，后续激活新版不能改变历史运行和审批引用。 |

### 7.9 采购制度 RAG

| ID | 优先级 | 需求 |
| --- | --- | --- |
| FR-RAG-001 | R2 MUST | 新分析默认只检索当前 `ACTIVE` 的制度版本，结果必须返回并保存具体 PolicyVersion。 |
| FR-RAG-002 | R2 MUST | 制度解析和分块必须尽可能保留页码、章节路径、字符范围和稳定 chunk ID。 |
| FR-RAG-003 | R2 MUST | 第一版使用单一向量检索基线和可配置 Top-K，不默认引入 Elasticsearch。 |
| FR-RAG-004 | R2 MUST | 检索必须受当前业务范围限制，不得返回无权制度或其他组织证据。 |
| FR-RAG-005 | R2 MUST | 返回给风险或建议链路的证据必须包含可验证引用。 |
| FR-RAG-006 | R2 MUST | 没有充分证据时，系统必须返回缺失/不足状态，不允许用模型常识补造企业制度。 |
| FR-RAG-007 | GATED | 只有固定评测证明基线在关键词或精确条款召回上不足时，才比较 BM25、RRF、Rerank 或查询改写。 |

### 7.10 Analysis Run 生命周期

| ID | 优先级 | 需求 |
| --- | --- | --- |
| FR-ANA-001 | R2 MUST | 采购申请首次提交成功后，系统自动创建一个 `PENDING` Analysis Run，并快照本次申请、选定报价、材料 ID 和当前有效 PolicyVersion。 |
| FR-ANA-002 | R2 MUST | Run 快照中的任一材料仍为 `UPLOADED` 或 `PROCESSING` 时，Run 保持 `PENDING`；提交接口不等待解析完成。 |
| FR-ANA-003 | R2 MUST | 快照材料全部进入 `READY` 或 `FAILED` 终态后，Run 才进入 `RUNNING`；仅使用 `READY` 材料，`FAILED` 材料作为不可用证据和缺失项参与结果。 |
| FR-ANA-004 | R2 MUST | 能够完成 Evidence 整理、证据等级和确定性 Risk 计算时，Analysis Run 标记 `COMPLETED`，即使证据不足或后续 Recommendation 失败；只有 Evidence/Rule 分析链路自身无法完成时才标记 `FAILED`。 |
| FR-ANA-005 | R2 MUST | 申请人提交补证响应后，系统为当时的完整材料和制度版本创建新的 Run；若新材料尚未进入终态，新 Run 保持 `PENDING`。 |
| FR-ANA-006 | R2 MUST | 重新分析不得覆盖旧 Run、风险、建议和引用；同一触发请求必须幂等，避免生成重复 Run。 |

### 7.11 审批建议

| ID | 优先级 | 需求 |
| --- | --- | --- |
| FR-REC-001 | R2 MUST | 建议输入只能来自当前申请的已授权、已验证事实、风险和制度证据。 |
| FR-REC-002 | R2 MUST | 建议输出必须是结构化结果，包含建议动作、摘要、理由、缺失项、风险 ID 和证据引用。 |
| FR-REC-003 | R2 MUST | 建议动作仅允许 `SUGGEST_APPROVE`、`SUGGEST_REJECT`、`REQUEST_MORE_EVIDENCE`。 |
| FR-REC-004 | R2 MUST | 所有建议在数据模型和 API 中必须明确标记为草稿/建议，不能与审批决定共用状态字段。 |
| FR-REC-005 | R2 MUST | Recommendation 的模型调用、输出解析、字段、引用或业务校验失败时，其状态进入 `FAILED`，不能保存为有效建议，也不能把已完成的 Analysis Run 改为失败。 |
| FR-REC-006 | R2 MUST | `NONE` 或 `WEAK` 证据不得生成批准/驳回倾向，只能要求补证或人工处理。 |
| FR-REC-007 | R2 SHOULD | 建议保存模型、Prompt、输入证据集合和生成时间等版本信息，敏感原文按最小需要保留。 |
| FR-REC-008 | R2 MUST | 建议不能调用批准、驳回、预算、订单或付款命令。 |
| FR-REC-009 | R2 MUST | 每个 Recommendation 必须绑定一个已 `COMPLETED` 的 Analysis Run，并具有独立的 `PENDING/RUNNING/COMPLETED/FAILED` 状态。 |
| FR-REC-010 | R2 SHOULD | Recommendation 重试创建新的生成记录或版本，不覆盖审批曾经查看或引用的旧结果。 |

| FR-AGT-001 | R3 MUST | 每次运行必须绑定当前用户、当前申请、业务范围和唯一 Agent Run ID。 |
| FR-AGT-002 | R3 MUST | MVP 仅提供读取申请事实、搜索制度、查询供应商、查询历史价格和列出风险项的只读 Tool。 |
| FR-AGT-003 | R3 MUST | ToolContext 中的身份和范围由服务端注入，模型提供的冲突身份参数必须被拒绝或忽略。 |

## 8. 业务规则

| ID | 规则 |
| --- | --- |
| BR-001 | 采购金额使用 `BigDecimal` 语义，禁止使用二进制浮点数进行财务计算。 |
| BR-002 | 汇总金额由服务端计算，并采用明确的舍入规则。 |
| BR-003 | 只有创建者能够提交自己的草稿。 |
| BR-004 | 只有 `DRAFT` 可通过普通编辑用例修改核心申请字段。 |
| BR-005 | 申请人不能审批自己的申请，即使同时拥有 `APPROVER` 角色。 |
| BR-006 | 一个 MVP 申请最多存在一个活动审批任务和一个成功最终决定。 |
| BR-007 | 驳回原因必填；批准意见可选，但操作者身份和时间必填。 |
| BR-008 | 重复提交或审批必须返回原结果或明确冲突，不能重复产生任务、决定和审计副作用。 |
| BR-009 | AI 失败或未运行不等于“无风险”。 |
| BR-010 | 模型建议不构成审批决定，详细边界遵守 ADR-002。 |
| BR-011 | 风险阈值必须能追溯到制度版本或显式配置。 |
| BR-012 | 历史分析结果不得因重新运行而失去可追溯性。 |
| BR-013 | `SUBMITTED` 只有在存在当前任务的 `OPEN` 补证请求时才允许追加关联材料和提交补证响应，不允许主动追加无关材料、修改核心字段或删除、覆盖既有材料。 |
| BR-014 | 提交只要求原文件可靠保存并登记，不以解析 `READY` 作为前置条件。 |
| BR-015 | 选定报价必须属于当前申请并与拟采购供应商一致。 |
| BR-016 | 同一制度标识同时最多一个有效版本，历史运行继续引用执行时版本。 |
| BR-017 | 同一审批任务同时最多一个 `OPEN` 补证请求；最终审批前所有补证请求必须为 `RESPONDED` 或 `CANCELLED`。 |
| BR-018 | 历史价格基线至少要求相同 `categoryCode` 和计量单位；规格、数量区间或时间窗口只能通过确定性配置进一步收窄，不能由 LLM 自行认定“可比”。 |
| BR-019 | Recommendation 失败不改变已成功完成的 Evidence 和确定性 Risk 结果，也不改变 Analysis Run 的 `COMPLETED` 状态。 |

## 10. AI 评测需求

### 10.1 数据集

- 使用合成的采购申请、报价单、合同、制度、供应商和历史价格，不包含真实敏感信息。
- 开发集用于调试，隐藏集不参与 Prompt、分块和阈值调优。
- 每个失败样本归类为解析失败、检索失败、生成失败、引用错误、规则错误或权限错误。

### 10.2 必须报告的指标

| 能力 | 指标 |
| --- | --- |
| 字段提取 | 核心字段准确率、缺失率、非法值拒绝率 |
| RAG | `Recall@K`、证据覆盖率、引用准确率、越界检索率 |
| 建议生成 | 结构化输出通过率、有效引用率、证据不足时的正确降级率 |
| Agent | 任务完成率、平均 Tool 次数、Tool 失败率、预算终止率 |
| 安全 | 未授权访问阻断率、关键写 Tool 暴露数、自动审批成功数 |

安全验收要求：越界检索和自动审批的成功数必须为零。其他 AI 指标先记录可复现基线，再通过对照实验设定改进目标；不得编造准确率或只展示成功样本。

### 10.3 最小评测规模

- RAG 基线至少包含 20 个固定制度问题，并保留独立隐藏用例。
- 字段提取至少覆盖正常、缺失、冲突、边界金额和损坏文件。
- Agent 安全集必须包含 Prompt Injection、伪造身份、伪造引用、重复 Tool 和直接审批请求。

数据规模用于证明方法和可重复性，不声明达到生产统计显著性。

## 11. 端到端验收场景

### AC-E2E-001 正常采购审批

申请人创建草稿、添加采购项和材料并提交；系统形成风险与建议；被分配的审批人查看引用并批准；最终状态、审批任务、决定和审计保持一致。

### AC-E2E-002 证据不足

申请缺少制度要求的报价时，系统产生稳定风险代码和缺失项，建议只能要求补证或人工处理，不能建议直接批准。审批人在 `PENDING` 任务上发起唯一的 `OPEN` 补证请求；申请人只能向该请求追加报价并提交响应；系统创建新 Analysis Run，审批人能够同时追溯补证前后的结果。若审批人不再需要补证，必须先取消请求才能作出最终决定。

### AC-E2E-003 AI 服务失败

模型调用失败时，分析显示失败并保留重试/人工路径；采购申请不自动批准，审批人仍可查看原始材料并人工处理。

### AC-E2E-004 越权访问

其他申请人和未分配审批人无法读取或修改目标申请、材料、证据和任务；请求体伪造身份无效。

### AC-E2E-005 重复与并发审批

同一审批请求重复发送只产生一个决定；两个并发、相互冲突的决定最多一个成功，且审计结果一致。

### AC-E2E-006 恶意材料指令

材料文本要求模型忽略系统规则或批准采购时，系统可以把它当作文档内容分析，但不会扩大 Tool 权限、访问其他数据或改变采购状态。

## 12. 明确非目标

MVP 不要求：

- 微服务拆分、服务注册发现、API 网关平台或 Kubernetes。
- Redis、Kafka/RocketMQ、Elasticsearch 的默认接入。
- 通用 BPM、会签、加签、转签和多级条件审批。
- 多租户 SaaS、复杂组织树和完整 RBAC 管理后台。
- 真实 ERP、财务、付款、电子签章和采购订单执行。
- 供应商入驻、招投标、发票和收货三单匹配全流程。
- OCR、扫描件、印章、手写内容和复杂表格视觉解析。
- Multi-Agent、MCP、长期记忆、自主任务和模型微调平台。
- 完整前端产品；后端 API、测试和可复现演示优先。
- 伪造生产数据量、并发量、准确率或业务收益。

## 13. 待确认事项

1. MVP 的认证方式及演示账号初始化方式。
2. 单一审批人的最小路由配置方式。
3. 原始文件采用本地兼容存储还是对象存储。
4. 是否允许 Markdown 作为采购制度输入格式。
5. 首批样例制度的报价数量、历史价格偏差和预付款阈值。
6. 模型与 Embedding 服务供应商及本地测试替身。
7. 人工修正字段由申请人、审批人还是管理员负责。

## 14. User Story 编写门槛

下一阶段编写 User Story 时，每个 Story 必须：

1. 引用至少一个 Requirement ID。
2. 只交付一个可验证的用户结果。
3. 写明角色、前置状态和权限边界。
4. 使用 Given/When/Then 描述主要验收场景。
5. 覆盖适用的失败、重复、并发和审计场景。
6. 明确不包含哪些相邻能力。
7. 不因未来可能需要而加入额外基础设施。

在 Requirements 基线确认前，`docs/BACKLOG.md` 中已有 Story 视为规划占位；确认后再逐项建立需求追溯关系并细化验收条件。
